# 연결 프로그램: slam_bridge → memmap 장면 스트림

`slam/`(Rust)의 `slam_bridge` 가 RGB-D 입력으로 장면마다 위치를 구하고, 위치 + 컬러 + 컬러에 맞춘 깊이를 memmap 으로 흘려보낸다. memmap 은 `--stream` 으로 받아 지금의 TUM·카메라 입력과 같은 지도·물체·씬그래프 단계를 돈다. `slam_bridge` 는 RTAB-Map 0.24.2 에서 우리 설정이 지나가는 경로(F2F 위치 추적 · 루프 클로저 · GTSAM 최적화)를 Rust 로 옮긴 것이고, PC 에서 C++ 원본 `rtab_bridge` 와 스트림·위치 파일·장면별 판단이 바이트까지 같다(모듈과 검증: [slam/README.md](../slam/README.md)). 아래에서 "RTAB-Map" 은 이 처리 방식을 가리킨다.

```
RealSense D435 (컬러 RGB8 + 깊이 Z16, 640×480@30)      TUM 폴더 재생(rgb.txt·depth.txt, 시험용)
        │ 깊이 → 컬러 정렬(io/realsense.rs, librealsense align)          │
        └──────────────┬───────────────────────────────────┘
                       ▼
     RTAB-Map 위치 추적(매 장, Odometry) + 지도 갱신(Rtabmap::process, DetectionRate 1/초)
                       │ 장면 위치 = 지도 보정 × 위치 추적 × 광학 축
                       ▼  쓰기 스레드(큐, 밀리면 버림 또는 기다림)
           표준출력·파일·이름 있는 파이프 ──→ memmap --stream -  (분할 → 점 지도·물체·씬그래프)
```

처리 순서(위치 추적 → 놓침이면 다시 잡기 → DetectionRate 로 지도 노드 고르기 → `Rtabmap::process`)는 RTAB-Map 의 `rtabmap-rgbd_dataset` 도구와 같다. 오프라인 위치 파일(`--gt`)도 이 도구로 만들었다.

## 쓰는 법

```bash
# 빌드: 기본은 TUM 재생만, --features realsense 면 카메라 입력(librealsense2 C API 링크)
cargo build --release --manifest-path slam/Cargo.toml
cargo build --release --features realsense --manifest-path slam/Cargo.toml

# 카메라 → memmap(실시간)
slam_bridge --realsense --config docs/rtabmap_pi.ini --send-every 2 \
  | memmap --stream - --every 1 --live 1 --seg <분할 모델> --max-depth 3.5 --out data/memory/live

# TUM 재생(카메라 없이): --rate 1 이면 찍은 시각대로(밀리면 건너뜀), 생략하면 최대 속도로 빠짐없이
slam_bridge --tum data/d435/rgbd_dataset_freiburg3_office_sync --config docs/rtabmap_pi.ini \
  | memmap --stream - --every 2 --seg models/yolo26s-seg.onnx --max-depth 3.5 --out data/memory/office_stream
```

| `slam_bridge` 인자(`rtab_bridge` 와 같음) | 뜻 |
|---|---|
| `--realsense [--align rs2] [--serial S] [--size 640x480] [--fps 30]` | RealSense 입력(IMU 는 켜지 않음) |
| `--tum <폴더> [--rate R]` | TUM 폴더 재생. 보정값은 memmap `tum.rs` 와 같이 폴더 이름으로(freiburg1·2·3), 폴더에 `calibration.txt`(fx fy cx cy, ETH3D 형식)가 있으면 그 값 |
| `--config <ini>` | RTAB-Map 설정(`[Core]`), 그 뒤 `--Group/Name 값` 으로 덮어씀 |
| `--out -\|<파일>` | 스트림 출력(기본 표준출력). 파일로 남겨 두면 `memmap --stream <파일>` 로 다시 돌릴 수 있음 |
| `--send-every N` | N 장마다 보냄(위치 추적은 모든 장면) |
| `--queue N`, `--block`·`--drop` | 쓰기 큐 길이(기본 4), 큐가 차면 기다림·가장 오래된 장면 버림. 기본은 최대 속도 재생 = 기다림, 카메라·`--rate` = 버림 |
| `--poses <파일>` | 보낸 위치(TUM 형식, OpenCV 카메라 → RTAB-Map 지도) |
| `--final-poses <파일>` | 끝에 최적화된 지도 노드 위치(TUM 형식, 같은 좌표) |
| `--reset-file <파일>` | 이 파일이 생기면 지우고 위치 추적·지도를 처음부터(뷰어 리셋 아이콘이 기억 폴더의 `reset.req` 를 만듦) |
| `--reloc-wait 초` | 놓친 뒤 같은 지도에서 다시 잡기만 시도하는 시간(기본 1) |
| `--stats <파일>` | 장면별 시간·놓침·새 지도·지도 보정·특징 수(CSV) |
| `--max-frames N` | 앞 N 장만 |
| `--reset-at N` | 시험용: N 번째 장면에서 리셋 파일이 생긴 것처럼 처음부터 |
| `--db <파일>` | `rtab_bridge` 만: RTAB-Map 데이터베이스로 남김(`rtabmap-databaseViewer`). `slam_bridge` 는 넘어감 |

로그는 표준오류로 나간다(표준출력은 스트림 전용).

### C++ 원본(비교 기준)

`bridge/src` 의 `rtab_bridge`(C++, RTAB-Map 0.24.2 라이브러리 링크)는 `slam_bridge` 의 비교 기준이고, 보드 실시간 스크립트가 지금 쓰는 프로그램이다(보드 ARM 에서 바이트 비교를 마치면 `slam_bridge` 로 바꿈). 인자·스트림은 같다. 빌드(WSL·보드, librealsense 가 없으면 TUM 재생만):

```bash
cmake -S bridge -B ~/build/bridge -G Ninja -DCMAKE_PREFIX_PATH="$HOME/opt/rtabmap;$HOME/opt/librealsense"
ninja -C ~/build/bridge
```

보드의 RTAB-Map·OpenCV·GTSAM 소스 빌드는 [board_bridge.md](board_bridge.md).

| `memmap` 인자 | 뜻 |
|---|---|
| `--stream -\|<파일>` | 장면 스트림 입력. 위치·깊이는 받은 그대로, 분할은 memmap 이 돌림. `--every N` 은 받은 장면 N 장마다 |
| `--no-level` | 받은 위치의 z 를 그대로 위로 씀(기본은 아래 "바닥 맞추기") |
| `--rebuild-every S`, `--kf-store-mb M`, `--no-rebuild` | 루프 클로저 뒤 다시 쌓기 간격(초, 기본 5, 0 = 끝에만)·장면 보관 예산(MB, 기본 3000)·끄기(아래 "루프 클로저 뒤 다시 쌓기") |

memmap 출력은 TUM 입력과 같고, 스트림이면 `poses_est.txt`(받아 쓴 위치, 수평 맞춘 세계)가 더 생긴다. 모든 입력에서 `poses_map.txt`(지도에 넣은 장면의 카메라 위치, 지도 좌표)가 생긴다.

## 스트림 형식

장면 하나 = 머리 176 바이트 + RGB8(`w×h×3`, 행 우선, R·G·B) + 깊이(`w×h` 개 u16). 장면 사이에 그래프 블록(아래)이 끼어 온다. 모든 수는 리틀 엔디언, 실수는 IEEE 754. 보내는 쪽이 닫으면 끝.

| 위치 | 형 | 칸 | 값 |
|---|---|---|---|
| 0 | char[4] | 표시 | `MMF1` |
| 4 | u32 | 머리 크기 | 176 |
| 8 | u32 | 상태 | 1 = 위치 놓침(위치 칸 무시), 2 = 이 장면에서 새 지도 시작, 4 = 이 장면에서 지도 보정(루프 클로저·최적화)이 바뀜, 8 = 맡아 둘 장면(1 과 함께 옴: 믿는 지도와 아직 안 이어진 새 지도의 위치·기준 노드가 들어 있음) |
| 12 | u32 | 지도 번호 | RTAB-Map 지도 번호(새 지도마다 늘어남) |
| 16 | u64 | 장면 번호 | 입력 순서(보내지 않은 장면도 셈) |
| 24 | f64 | 시각 | 초(TUM: 파일 시각, RealSense: 컬러 장면 시각) |
| 32 | f64[12] | 위치 | 3×4 행 우선 `[R | t]`: OpenCV 카메라 → 세계 |
| 128 | f64[4] | 보정값 | fx, fy, cx, cy(컬러, 왜곡 없음) |
| 160 | u32 ×2 | 크기 | w, h |
| 168 | f32 | 깊이 배율 | 깊이 값 / 미터(RealSense 1000 = mm, TUM 5000). 0 = 깊이 없음 |
| 172 | u32 | 기준 노드 | 이 장면의 기준 RTAB-Map 지도 노드 id(`getLastLocationId()`, 0 = 없음). 장면 위치 = 그 노드 위치 × 상대 위치 |

그래프 블록 = 머리 16 바이트 + 노드마다 104 바이트. 지도 갱신(`Rtabmap::process`) 뒤 새로 생기거나 움직인(3×4 행렬 원소가 1e-3 넘게 바뀐) 노드만 담아 그 장면보다 먼저 보낸다. 쓰기 큐가 차도 버리지 않는다.

| 위치 | 형 | 칸 | 값 |
|---|---|---|---|
| 0 | char[4] | 표시 | `MMG1` |
| 4 | u32 | 머리 크기 | 16 |
| 8 | u32 | 노드 수 | n |
| 12 | u32 | 리셋 | 보통 0. 1 이면 리셋 블록(노드 0 개): memmap 이 지도·물체를 비우고 새 실행으로 다시 시작 |
| 16 + 104·i | u32, u32 | 노드 id, 맡아 둠 | `getLocalOptimizedPoses()` 의 id. 맡아 둠 1 = 믿는 지도와 아직 안 이어진 새 지도의 노드, 0 = 믿는 지도의 노드 |
| 24 + 104·i | f64[12] | 노드 위치 | 3×4 행 우선, OpenCV 카메라 → 세계(장면 위치와 같은 좌표: 노드 위치 × opticalRotation) |

깊이는 컬러 화소 격자에 맞춘 것. memmap 은 `값 / 깊이 배율` 로 미터를 만든다(TUM 입력 `tum.rs` 와 같은 계산이라 같은 영상이면 같은 수).

## 좌표 약속

| | 카메라 축 | 세계 축 |
|---|---|---|
| memmap(`r`, `p`) | OpenCV: x 오른쪽, y 아래, z 앞 | x·y 수평, **z 위**(바닥·점유 지도·방 나누기가 z 를 위로 씀) |
| RTAB-Map 위치 추적 | 몸체: x 앞, y 왼쪽, z 위(ROS) | 지도: 첫 장면의 몸체 축(IMU 없으면 z 는 처음 든 카메라의 위) |
| 몸체 → 광학 축 | `CameraModel::opticalRotation()` = `[[0,0,1],[-1,0,0],[0,-1,0]]`(열 = 광학 x·y·z 를 몸체로) | |

- 연결 프로그램이 보내는 위치 = `지도 보정 × 위치 추적 × opticalRotation`. 첫 장면은 정확히 `opticalRotation` 이 되고, 이것은 memmap 웹캠 입력의 첫 자세(`r0 = [[0,0,1],[-1,0,0],[0,-1,0]]`, 수평으로 앞을 봄)와 같다. 그래서 회전을 따로 바꾸지 않는다.
- **바닥 맞추기**: RTAB-Map 지도의 z 는 첫 장면 카메라가 기운 만큼 기울어 있다. memmap 은 웹캠 입력과 같은 방법(장면마다 RANSAC 으로 찾은 수평면 법선 15 개 이상이 10° 안에서 합의)으로 위쪽을 정해 그 뒤 오는 모든 위치에 같은 회전을 곱한다. 합의 전 장면은 지도에 넣지 않는다.
- 높이: memmap 이 첫 장면의 바닥 높이(카메라 아래 깊이 점 95 %)로 원점을 바닥에 맞춘다(TUM 입력과 같음).
- 코드로 확인한 것(검증 표의 `자세 차이`): 보낸 위치를 정답에 맞춘 뒤 카메라 자세 차이가 사무실 1–2°, 책상 3–6°. 몸체 축을 그대로 보냈다면 opticalRotation 의 회전각인 120° 가 나온다. memmap 이 받아 쓴 위치(`poses_est.txt`)를 보낸 위치에 맞추면 위치 차이 0, 자세 차이 0°(바닥 맞추기 회전 한 번만 다름).

## 놓침·새 지도·루프 클로저

- 위치를 못 구한 장면은 상태 1 로 보내고 memmap 은 지도·물체에 넣지 않는다(개수는 결과 JSON `stream_lost`).
- 놓치면 먼저 같은 지도에서 다시 잡는다: 놓치기 전 장면 6 개(0.4 초 간격)를 기준 장면으로 들고 있다가, 지금 장면과 특징점을 직접 맞춰(`RegistrationVis`, 맞은 점 25 개 이상) 위치를 구하고 위치 추적을 그 위치에서 잇는다. 한 장면에 기준 장면 둘씩 돌아가며 맞춘다.
- `--reloc-wait`(1 초) 안에 못 잡으면 위치 추적을 마지막 위치에서 다시 시작하고 `triggerNewMap()` 으로 새 지도를 연다. 이 위치는 "마지막 위치에서 이어 붙인" 값이라 그동안 카메라가 움직였으면 틀리다. 그래서 새 지도의 장면은 놓침(상태 1)으로 보내고, 루프 클로저로 믿던 지도와 다시 이어진 장면부터 위치를 보낸다. 기다리는 동안은 지도 갱신을 1 초에 4 번으로 올려 더 자주 찾는다.
- **맡아 두기**: 새 지도 안에서는 위치 추적이 다시 이어지므로, 그 장면을 상태 1 + 8 로 새 지도 좌표의 위치·기준 노드와 함께 보내고 새 지도의 노드는 그래프 블록에 맡아 둠 1 로 보낸다. memmap 은 맡아 둘 장면을 분할까지 해서 보관만 하고(지도·물체·뷰어 위치에는 넣지 않음), 루프 클로저로 두 지도가 이어지면 연결 프로그램이 그 노드들을 맡아 둠 0 과 고친 위치로 다시 보내 다음 다시 쌓기가 보관한 장면을 지도에 넣는다. 끝까지 안 이어진 지도의 장면은 지도에 들어가지 않는다. 개수는 연결 프로그램 끝 요약의 "맡긴 장면", memmap 결과 JSON `stream_held`(`frames` 받은 수, `joined` 지도에 들어간 수, `waiting` 안 이어진 수).
- 믿던 지도가 3 초 몫도 안 될 때 놓쳐 못 잡으면 리셋과 같이 처음부터 다시 한다(리셋 블록을 보냄).
- 루프 클로저로 지도 보정이 바뀌면 그 장면부터 위치가 보정된 좌표로 오고(상태 4), 그 앞에 움직인 노드를 담은 그래프 블록이 온다.

### 루프 클로저 뒤 다시 쌓기(memmap)

- memmap 은 지도에 넣은 장면을 기준 노드와 그 노드에서 본 상대 위치로 보관한다(`kfstore.rs`). 상대 위치는 받을 때 `기준 노드 위치⁻¹ × 장면 위치` 로 구한다. RTAB-Map 에서 마지막 노드 위치 = 지도 보정 × 그 노드의 오도메트리 위치라, 이 값은 오도메트리 상대 움직임과 같고 루프 클로저로 바뀌지 않는다.
- **점유 지도·점 지도·물체·지나온 길**: 그래프 블록 뒤 노드가 2 cm 또는 1° 넘게 움직였으면 `--rebuild-every` 초(기본 5)에 한 번까지 작업 스레드가 비우고 보관한 장면을 `지금 노드 위치 × 상대 위치` 로 처음부터 다시 쌓는다(실시간 장면과 같은 `map_frame`, 물체 병합 후처리는 15 장마다). 스트림이 끝났을 때 표시가 남아 있으면 한 번 더 쌓아 결과 지도·물체·`poses_map.txt` 가 끝난 그래프를 따른다. 물체 id 는 이어서 쓴다.
- 장면 보관은 줄인 형태: 깊이는 4 화소 간격, 검출 상자 안은 컬러·깊이 그대로(손실 없는 압축, 줄 안 차분 + LZ4), 장당 약 0.45 MB. 점유 지도는 16 화소 간격(8 + 16k) 깊이만 읽어 받은 값과 같고, 물체 점·사진은 상자 안만 읽는다. 사라짐 판정(보여야 할 자리의 깊이)만 4 화소 간격 깊이를 쓴다. 점 지도는 점 작업 스레드가 장면마다 남긴 점 격자(거른 뒤 `--scene-step` 간격의 깊이·색, LZ4)로 다시 쌓는다.
- 보관 예산 `--kf-store-mb`(기본 3000): 넘으면 보관한 장면을 하나 걸러 버리고 이후 두 배 간격으로 보관한다. `--rebuild-every 0` 은 끝에만, `--no-rebuild` 는 보관·다시 쌓기 없이 받은 위치 그대로 쌓는다.
- 기준 노드를 모르는 장면(노드가 생기기 전, 다른 지도에서 끊긴 노드)은 받은 위치 그대로 쌓는다.

### 3D 점 지도(옥트리 LOD, memmap `maps.rs`, 뷰어)

memmap 은 늘 점 지도를 만든다(Potree 방식으로 보여 줌).

- **점 고르기**: 장면마다 `--scene-step`(기본 2) 화소 간격으로 깊이 점을 만들되 깊이 경계(5×5 에서 8 % 넘게 들쭉날쭉)와 비스듬히 본 면(이웃 ±2 화소로 만든 법선과 시선의 코사인 0.3 미만)을 빼고 `--pts-depth`(기본 3 m) 안만 쓴다. 점은 `--scene-vox` 칸(시연 0.006 m)에 모아 칸 안 평균 위치로, 색은 가장 가까운 거리의 2 배 안에서 본 관측의 평균. 칸을 본 키프레임이 `--pts-obs`(기본 3) 장에 닿으면 점이 된다(한두 장에만 맞은 잡음 점은 남지 않음). 칸 하나 14 바이트.
- **옥트리**: 수준 L(0–5)의 점 간격 = 칸 × 2^(5−L), 노드 한 변 = 간격 × 32. 새 점은 자기 칸이 아직 빈 가장 굵은 수준의 노드 하나에만 들어간다(겹침 없음, Potree 와 같이 부모가 성기게 전체를 덮고 자식이 촘촘함을 더함).
- **파일**: `scene/<판>/n<L>_<x>_<y>_<z>.bin`(점마다 노드 상자 안 u16 × 3 위치, 그 뒤 RGB — 점당 9 바이트, 뷰어가 해석 없이 그대로 올림)과 노드 목록 `scene/<판>/octree.json`(`[수준, x, y, z, 점 수, 판]`). `view.json` 의 `scene_points.octree` 에 판·목록 판 번호가 들어간다.
- **늘려 쓰기**: 1 초(실시간)마다 새 점을 노드에 넣고, 점이 처음 생겼거나 10 % 넘게 는 노드만 다시 쓴다. 한 번에 다시 쓰는 점은 30 만 개까지(넘는 노드는 다음 번), 끝에는 남은 노드를 모두 쓴다.
- **루프 클로저**: 다시 쌓기 작업 스레드가 점 지도도 처음부터 쌓고 모든 노드 파일 바이트까지 만든다. 본 스레드는 갈아 끼우며 새 판 폴더에 쓰고 옛 판 폴더를 지운다. 판 번호가 바뀌면 뷰어는 받은 노드를 비우고 새로 받는다.

검증(WSL, 사무실 녹화 스트림, `--depth kinect --seg yolo26s-seg.onnx --every 2 --max-depth 3.5 --scene-vox 0.006`, 2026-11-08): 점 4.53 M(예전 0.005 m 네모 점 13.9 M · 199 MB → 노드 1,550 개 43 MB), 지도 넣기 22 ms/장, 노드 쓰기 한 번 60–170 ms(장면 50 장 몫, 실시간 1 초 몫은 그 약 1/7), 점 지도 메모리 약 400 MB(최대 RSS 3.2 GB 중 보관 장면 1.3 GB), 다시 쌓기 작업 스레드 11–31 초. 물체·위치는 점 지도와 무관하게 같다(fr1_desk TUM 입력 main 과 물체 목록 일치). 그림: `docs/results/potree_before_*.png` → `potree_after_*.png`(Low: `potree_after_low.png`, 0.8 M 점), Potree 예제 `potree_reference.png`. 먼 시점은 Potree 처럼 촘촘하고 윤곽이 서지만, 가까이서는 Kinect 깊이 잡음으로 점이 알갱이처럼 보이고 책상 글자는 읽히지 않는다.

## 검증 (WSL Ubuntu 24.04, TUM 재생, 2026-11-05)

아래 두 절은 C++ `rtab_bridge` 로 잰 값이다. `slam_bridge` 는 지금 ini(`docs/rtabmap_pi.ini`, GFTT/BRIEF + GTSAM)로 같은 입력을 넣으면 출력이 바이트까지 같아 그 조합의 정확도가 같다. ORB · g2o 조합은 C++ 원본에만 있다.

`bridge/tools/check_tum.sh` 로 시퀀스마다 세 번 돌려 견줌. 이 표는 RTAB-Map 0.24.2 를 Ubuntu 패키지(OpenCV 4.6 xfeatures2d 없음, g2o)로 빌드한 GFTT/ORB · g2o 조합으로 잰 것이다. 지금 ini 의 GFTT/BRIEF · GTSAM 과의 비교는 아래 "특징·최적화기 비교". memmap 은 ONNX Runtime CPU 로 YOLO26s-seg 분할, `--depth kinect --every 2`, 최대 거리 사무실·책상 3.5 m, 복도 4 m.

- **기준**: 같은 설정 + 모든 장면을 지도 노드로 끝까지 돌려 최적화한 위치 → `memmap --tum --gt`(오프라인 경로).
- **같은 위치 오프라인**: 스트림 실행이 보낸 위치 파일 그대로 → `memmap --tum --gt`. 스트림과 위치가 같고 입력 경로만 다르다.
- **스트림**: `rtab_bridge | memmap --stream -`(보드와 같은 설정, 장면이 들어올 때의 위치).

위치 오차는 정답 기준 `ate`(맞춘 뒤 RMSE).

- **스트림 위치는 기준보다 덜 정확**: 기준은 끝난 뒤 모든 장면을 루프 클로저까지 반영해 다시 최적화한 위치이고, 스트림은 그 장면이 들어온 순간의 위치다. 사무실 3.8 → 6.4 cm, 책상 4.2 → 10 cm, 복도 0.25 → 0.34 m. 지도에는 다시 쌓기가 끝난 그래프 위치를 반영한다(위 표의 스트림 줄은 다시 쌓기를 넣기 전 측정).
- 같은 설정도 실행마다 흔들린다(RTAB-Map 안 병렬 처리): 사무실 보낸 위치 4.0 · 4.9 · 6.4 cm, 책상 지도 노드 4.4–10.4 cm.

### 특징·최적화기 비교 (WSL, 2026-11-08)

`rtab_bridge --tum <시퀀스> --config <ini> --out /dev/null` 을 조합마다 세 번, 다섯 조합을 서로 다른 코어에서 동시에 돌림. 오차는 정답 기준 `ate`, "끝 그래프" = `--final-poses`(최적화된 지도 노드), "보낸 위치" = `--poses`(장면이 들어온 순간). 세 시퀀스 모두 놓침 0(정확도 우선 + ORB 책상 한 번만 놓침 1).

## 시간

`slam_bridge`(PC WSL, 최대 속도 재생): fr1 책상 268 장/초, 복도 232 장/초로 C++ 원본의 약 2.2 – 2.3 배. 본 스레드 계산은 장면당 2.8 – 3.1 ms(위치 추적 평균 2.6 – 2.9 ms)라 벽시계는 PNG 읽기 스레드가 정한다. 기록: [performance_log.md](performance_log.md) "Rust 위치 프로그램(slam_bridge) 통합 재검증".

C++ `rtab_bridge` 값([performance_log.md](performance_log.md) "연결 프로그램 시간"): PC 코어 하나에서 18 ms/장(그중 위치 추적 9.8 ms, TUM PNG 읽기 8 ms), 지도 갱신 1 초에 한 번 14 ms(최대 44 ms). 30 장/초 재생에서 위치 추적은 장면을 놓치지 않고, memmap 이 느리면 쓰기 큐에서 장면이 버려진다.

장면 넘기기(쓰기 스레드 0.8 ms/장 + memmap 읽기 스레드 0.5 ms/장)는 본 스레드 밖에서 돈다. 파이프 버퍼는 1 MB, 카메라가 준 RGB 사진은 그대로 쓰고, 큐에 든 장면은 저마다 제 버퍼를 가진다. memmap 은 사진·깊이를 받을 자리에 바로 읽는다.

## 깊이 정렬 바꿔 끼우기

깊이를 컬러 격자로 옮기는 곳은 `slam/src/io/realsense.rs` 하나다(`rtab_bridge` 는 `bridge/src/depth_align.cpp`). `--align <이름>` 으로 고르고, 지금은 `rs2`(librealsense align, CPU).
