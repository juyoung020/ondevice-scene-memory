# 속도 최적화 정리 (발표용)

프로젝트 전체의 속도 개선을 구성 요소별로 모은 문서. 숫자는 모두 [`performance_log.md`](performance_log.md)에서 옮겼고, 각 줄의 "출처"는 그 문서의 절 제목이다(앞의 `PL ›` = `performance_log.md ›`).

- **PC** = 데스크톱 Ryzen 9 9950X(대부분 WSL Ubuntu 24.04). **보드** = Raspberry Pi 5 + DX-M1 NPU.
- **보드 흉내** = PC 에서 `taskset` 으로 코어를 2–4 개로 묶고 `--slow 3`(CPU 일 3 배)·`--seg-min-ms 97`(NPU 분할 시간)·`--stream-rate 1`(찍은 시각대로)을 준 실행.
- 데이터: **사무실** = TUM fr3/long_office_household(2,585 장, `--every 2` 이면 키프레임 1,293), **책상** = TUM fr1/desk·desk2, **복도** = D435i digiteo2, ETH3D SLAM 영상.
- "결과 같음" = 같은 입력에서 출력 파일(위치·물체·표면)이 바이트까지 같거나, 문서에 적힌 범위에서 같음.

- "처음"은 그 모듈을 처음 잰 값, "지금"은 현재 코드. 전체 줄의 처음은 파이썬 첫 판(PC), 지금은 Rust(PC) · Rust + NPU(보드)라 기계가 다르다.
- 위치(Rust) 줄은 C++ RTAB-Map · OpenCV · GTSAM 을 Rust 로 옮긴 결과이고, 원본과 같은 입력으로 비트 비교했다(아래 4 절). 장면 읽기의 원본 숫자는 RTAB-Map 과 함께 돌 때 잰 값이다.
- 위치 추적과 위치 프로그램 전체 줄은 조각을 합친 `slam_bridge` 와 C++ `rtab_bridge` 를 같은 조건(PC WSL, 데이터를 WSL 디스크에 두고 최대 속도 재생, fr1_desk · 복도 녹화, 2 번 잰 범위)으로 돌려 잰 값이다. 보드 숫자는 보드에서 같은 비교로 더한다.
- 위치 프로그램 전체 줄은 번들 조정 개선 전에 잰 값이다. 지금 Rust 는 장면당 계산이 약 3 ms 아래라 녹화 재생에서는 PNG 읽기가 전체 속도를 정하고, 실시간 카메라에서는 그 읽기가 없다.

### 가장 큰 개선 7 가지

1. **파이썬 → Rust 누적 지도**: 지도·물체·기록 1,100 ms → 17 ms(PC, 약 65 배), 키프레임 1.1 s → 85 ms(13 배). 지도를 다시 정렬하는 대신 해시 칸에 새 점만 더함.
2. **분할과 지도 겹치기**: PC 85 → 60 ms(1.4 배), 보드 113 → 85 ms(1.3 배). 결과 같음.
3. **NPU 장면 여러 장 함께 올리기**: 녹화 600 장 53 → 25 초(2.1 배), 분할 8.2 → 16.1 /초. `poses_map.txt` 바이트까지 같음.
4. **보드 뷰어 EDL 기본 끔**: Chromium 31.6 → 59.3 프레임/초, 100 ms 넘는 멈춤 26 → 0.
5. **뷰어 움직이는 동안 가볍게**: 약한 GPU 흉내 점 지도 10.6 → 46.6 장/초(4.4 배), 표면 25.5 → 58.9 장/초(2.3 배).
6. **직접 방식 위치 추적을 상주 스레드 풀로**: 위치만 추적 장면 12.8 → 6.2 ms, 위치 단계 17.4 → 8.0 ms(PC, 결과 같음).
7. **느린 코어에서 본 스레드 멈춤 나누기**: `--slow 5` 버린 장면 5–13 → 0, 본 스레드 최대 506–521 → 56–58 ms(코어 2 개).

- FLANN 단어 사전: 이진 기술자를 비트로 묶어 두고 popcount 로 L1 거리를 구한다(값은 비트까지 같음). 메모리는 32 배 작다.
- 입출력: 컬러와 깊이 PNG 를 나란히 풀고, 쓰기에서 BGR→RGB 를 받은 버퍼 안에서 바로 바꾼다(복사 없음). 읽기의 원본 숫자는 RTAB-Map 과 함께 돌 때 잰 값이라 조건이 조금 다르다.
- 뷰어 벽: C++ 를 없애고 Rust 로만 돈다. 속도는 원본과 같다.
- 루프 클로저: 사전 찾기의 질의 300 개를 64 개씩 나눠 여러 스레드에서 찾고(질의끼리 상관없어 결과 같음), 새 단어끼리 비교를 8 바이트 popcount 로 바꿨다. 기본 꺼진 변형 `Rust/DictChecks`(사전 찾기 checks 32 → 16 · 8)는 긴 사무실에서 찾기 73 → 60 · 54 ms 로 조금 빠르지만 루프 가설이 13 → 8 · 7 번으로 줄어 쓰지 않는다.
