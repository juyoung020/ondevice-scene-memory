# 위치 프로그램 → 물체 기억: 장면 넘기기

`slam/`(Rust)의 위치 프로그램이 RGB-D 입력으로 장면마다 위치를 구하고, 위치 + 컬러 + 컬러에 맞춘 깊이를 물체 기억(memmap)으로 넘긴다. 둘은 실행 파일 `ondevice` 한 프로세스에서 돌고(`ondevice --slam "…"`), 물체 기억은 받은 장면으로 TUM 입력과 같은 지도·물체·씬그래프 단계를 돈다. 위치 프로그램의 구조(광류 + IMU 앞단, MegaLoc · XFeat 루프, 자세 그래프)는 [slam.md](slam.md).

```
RealSense D435 (컬러 RGB8 + 깊이 Z16, 640×480@30)      TUM 폴더 재생(rgb.txt·depth.txt, 시험용)
        │ 깊이 → 컬러 정렬(rsdriver, tools::fast_align = rs2::align 규칙) │
        └──────────────┬───────────────────────────────────┘
                       ▼
     위치 추적(광류 + IMU, 매 장) + 지도 노드(1 초) → 루프 · 자세 그래프(따로 도는 스레드)
                       │ 장면 위치 = 지도 보정 × 위치 추적 × 광학 축
                       ▼  쓰기 스레드(큐, 밀리면 버림 또는 기다림)
           메모리 큐(--slam) · 장면 스트림 파일(ondevice slam --out) ──→ 물체 기억(분할 → 점 지도·물체·씬그래프)
```


## 쓰는 법

장면은 두 가지로 넘긴다. 결과(기억 폴더)는 두 방식이 바이트까지 같다.

- **한 프로세스(기본):** `ondevice --slam "<위치 인자>" …`. 위치 루프(`slam::app`)가 같은 프로세스의 스레드로 돌고, 장면은 아래 스트림 형식으로 바꾸지 않고 메모리 큐(`slam::stream::Writer::channel`)로 넘어간다. 컬러·깊이 버퍼는 PNG·카메라에서 채운 그대로 memmap 까지 옮겨지고(복사 0 번), 큐 길이·`--block`/`--drop`·그래프 블록을 버리지 않는 규칙·리셋 블록 차례는 파이프와 같다. `--serve "<포트> …"` 를 더하면 뷰어 서버(sgview)도 같은 프로세스에서 뜨고, 기억 폴더에 쓴 파일을 메모리에서 보낸다.
- **장면 스트림:** `ondevice slam … --out <파일>` 로 위치만 돌려 스트림을 남기고 `ondevice --stream <파일> …` 로 다시 돌린다(같은 녹화로 설정을 바꿔 볼 때). 스트림 형식 쓰기·읽기는 `slam::stream` 하나다.

```bash
# 빌드(저장소 맨 위 작업 공간): target/release/ondevice
cargo build --release

# 카메라 → 위치 추적 → 물체 기억 → 뷰어, 한 프로세스(실시간). D435 입력은 rsdriver(V4L2 · UVC 직접, 리눅스 빌드)
ondevice --slam "--realsense --send-every 2" \
  --every 1 --live 1 --seg <분할 모델> --max-depth 3.5 --out data/memory/live --serve "8091 --bind 0.0.0.0"

# TUM 재생(카메라 없이): --rate 1 이면 찍은 시각대로(밀리면 건너뜀), 생략하면 최대 속도로 빠짐없이
ondevice --slam "--tum data/d435/rgbd_dataset_freiburg3_office_sync" \
  --every 2 --max-depth 3.5 --out data/memory/office_stream

# 같은 것을 장면 스트림 파일로(위치만 한 번, 물체 기억은 몇 번이고)
ondevice slam --tum data/d435/rgbd_dataset_freiburg3_office_sync --out data/office.mmf
ondevice --stream data/office.mmf --every 2 --max-depth 3.5 --out data/memory/office_stream
```

`--slam` · `--serve` 의 인자는 공백으로 나눈다(경로에 공백이 없어야 함). 명령줄은 시작할 때 한 번 읽어 위치 · 물체 기억 · 뷰어 설정으로 나누고, 잘못된 위치 인자는 스레드를 띄우기 전에 멈춘다. `ondevice view <기억 폴더> …` 는 뷰어만 띄운다.

| 위치 인자(`--slam "…"` · `ondevice slam …`) | 뜻 |
|---|---|
| `--realsense [--serial S] [--size 640x480] [--fps 30] [--camera-profile librealsense\|tracking] [--exposure ms \| --ae-cap ms] [--gain 0..128]` | D435 입력(rsdriver, IMU 는 켜지 않음). 제어 묶음은 [realsense_input.md](realsense_input.md) |
| `--tum <폴더> [--rate R]` | TUM 폴더 재생. 보정값은 물체 기억의 TUM 입력과 같이 폴더 이름으로(`common::tum`)(freiburg1·2·3), 폴더에 `calibration.txt`(fx fy cx cy, ETH3D 형식)가 있으면 그 값 |
| `--out -\|<파일>` | 스트림 출력(기본 표준출력, `--slam` 에서는 쓰지 않음). 파일로 남겨 두면 `ondevice --stream <파일>` 로 다시 돌릴 수 있음 |
| `--send-every N` | N 장마다 보냄(위치 추적은 모든 장면) |
| `--queue N`, `--block`·`--drop` | 쓰기 큐 길이(기본 4), 큐가 차면 기다림·가장 오래된 장면 버림. 기본은 최대 속도 재생 = 기다림, 카메라·`--rate` = 버림 |
| `--poses <파일>` | 보낸 위치(TUM 형식, OpenCV 카메라 → 지도) |
| `--final-poses <파일>` | 끝에 최적화된 지도 노드 위치(TUM 형식, 같은 좌표) |
| `--reset-file <파일>` | 이 파일이 생기면 지우고 위치 추적·지도를 처음부터(따로 띄운 뷰어의 리셋 아이콘이 기억 폴더의 `reset.req` 를 만듦. 한 프로그램 `--serve` 는 인자 없이 리셋 버튼이 됨) |
| `--stats <파일>` | 장면별 시간·놓침·새 지도·지도 보정·특징 수(CSV) |
| `--max-frames N` | 앞 N 장만 |
| `--reset-at N` | 시험용: N 번째 장면에서 리셋 파일이 생긴 것처럼 처음부터 |

로그는 표준오류로 나간다(표준출력은 스트림 전용).

| 물체 기억 인자 | 뜻 |
|---|---|
| `--slam "<위치 인자>"` · `--stream -\|<파일>` | 같은 프로세스의 위치 프로그램 · 장면 스트림 입력. 위치·깊이는 받은 그대로, 분할은 물체 기억이 돌림.|<파일>` · `--slam "<slam_bridge 인자>"` | 장면 스트림 입력 · 같은 프로세스의 위치 프로그램. 위치·깊이는 받은 그대로, 분할은 memmap 이 돌림. `--every N` 은 받은 장면 N 장마다 |
| `--rebuild-every S`, `--kf-store-mb M` | 루프 클로저 뒤 다시 쌓기 간격(초, 기본 5, 0 = 끝에만)·장면 보관 예산(MB, 기본 3000)(아래 "루프 클로저 뒤 다시 쌓기") |

기억 폴더는 TUM 입력과 같고, 스트림이면 `poses_est.txt`(받아 쓴 위치, 수평 맞춘 세계)가 더 생긴다. 모든 입력에서 `poses_map.txt`(지도에 넣은 장면의 카메라 위치, 지도 좌표)가 생긴다.

## 스트림 형식

장면 하나 = 머리 176 바이트 + RGB8(`w×h×3`, 행 우선, R·G·B) + 깊이(`w×h` 개 u16). 장면 사이에 그래프 블록(아래)이 끼어 온다. 모든 수는 리틀 엔디언, 실수는 IEEE 754. 보내는 쪽이 닫으면 끝.

| 위치 | 형 | 칸 | 값 |
|---|---|---|---|
| 0 | char[4] | 표시 | `MMF1` |
| 4 | u32 | 머리 크기 | 176 |
| 8 | u32 | 상태 | 1 = 위치 놓침(위치 칸 무시), 2 = 이 장면에서 새 지도 시작, 4 = 이 장면에서 지도 보정(루프 클로저·최적화)이 바뀜, 8 = 맡아 둘 장면(1 과 함께 옴: 믿는 지도와 아직 안 이어진 새 지도의 위치·기준 노드가 들어 있음) |
| 12 | u32 | 지도 번호 | 지도 번호(늘 0: 지도는 하나) |
| 16 | u64 | 장면 번호 | 입력 순서(보내지 않은 장면도 셈) |
| 24 | f64 | 시각 | 초(TUM: 파일 시각, RealSense: 컬러 장면 시각) |
| 32 | f64[12] | 위치 | 3×4 행 우선 `[R | t]`: OpenCV 카메라 → 세계 |
| 128 | f64[4] | 보정값 | fx, fy, cx, cy(컬러, 왜곡 없음) |
| 160 | u32 ×2 | 크기 | w, h |
| 168 | f32 | 깊이 배율 | 깊이 값 / 미터(RealSense 1000 = mm, TUM 5000). 0 = 깊이 없음 |
| 172 | u32 | 기준 노드 | 이 장면의 기준 지도 노드 id(마지막 노드, 0 = 없음). 장면 위치 = 그 노드 위치 × 상대 위치 |

그래프 블록 = 머리 16 바이트 + 노드마다 104 바이트. 지도 갱신(`Rtabmap::process`) 뒤 새로 생기거나 움직인(3×4 행렬 원소가 1e-3 넘게 바뀐) 노드만 담아 그 장면보다 먼저 보낸다. 쓰기 큐가 차도 버리지 않는다.

| 위치 | 형 | 칸 | 값 |
|---|---|---|---|
| 0 | char[4] | 표시 | `MMG1` |
| 4 | u32 | 머리 크기 | 16 |
| 8 | u32 | 노드 수 | n |
| 12 | u32 | 리셋 | 보통 0. 1 이면 리셋 블록(노드 0 개): memmap 이 지도·물체를 비우고 새 실행으로 다시 시작 |
| 16 + 104·i | u32, u32 | 노드 id, 맡아 둠 | `getLocalOptimizedPoses()` 의 id. 맡아 둠 1 = 믿는 지도와 아직 안 이어진 새 지도의 노드, 0 = 믿는 지도의 노드 |
| 24 + 104·i | f64[12] | 노드 위치 | 3×4 행 우선, OpenCV 카메라 → 세계(장면 위치와 같은 좌표: 노드 위치 × opticalRotation) |

깊이는 컬러 화소 격자에 맞춘 것. memmap 은 `값 / 깊이 배율` 로 미터를 만든다(TUM 입력 `tum.rs` 와 같은 계산이라 같은 영상이면 같은 수).

## 좌표 약속

| | 카메라 축 | 세계 축 |
|---|---|---|
| memmap(`r`, `p`) | OpenCV: x 오른쪽, y 아래, z 앞 | x·y 수평, **z 위**(바닥·점유 지도·방 나누기가 z 를 위로 씀) |
| 위치 추적 | 몸체: x 앞, y 왼쪽, z 위(ROS) | 지도: 첫 장면의 몸체 축(IMU 없으면 z 는 처음 든 카메라의 위) |
| 몸체 → 광학 축 | `CameraModel::opticalRotation()` = `[[0,0,1],[-1,0,0],[0,-1,0]]`(열 = 광학 x·y·z 를 몸체로) | |

- 연결 프로그램이 보내는 위치 = `지도 보정 × 위치 추적 × opticalRotation`. 첫 장면은 정확히 `opticalRotation` 이 되고, 이것은 물체 기억이 쓰는 첫 자세(`r0 = [[0,0,1],[-1,0,0],[0,-1,0]]`, 수평으로 앞을 봄)와 같다. 그래서 회전을 따로 바꾸지 않는다.
- **바닥 맞추기**(IMU 없을 때): 지도의 z 는 첫 장면 카메라가 기운 만큼 기울어 있다(IMU 모드는 위치 프로그램이 중력으로 맞춰 보냄, 깃발 `GRAVITY`). 물체 기억은 (장면마다 RANSAC 으로 찾은 수평면 법선 15 개 이상이 10° 안에서 합의)으로 위쪽을 정해 그 뒤 오는 모든 위치에 같은 회전을 곱한다. 합의 전 장면은 지도에 넣지 않는다.
- 높이: memmap 이 첫 장면의 바닥 높이(카메라 아래 깊이 점 95 %)로 원점을 바닥에 맞춘다(TUM 입력과 같음).
- 코드로 확인한 것(검증 표의 `자세 차이`): 보낸 위치를 정답에 맞춘 뒤 카메라 자세 차이가 사무실 1–2°, 책상 3–6°. 몸체 축을 그대로 보냈다면 opticalRotation 의 회전각인 120° 가 나온다. memmap 이 받아 쓴 위치(`poses_est.txt`)를 보낸 위치에 맞추면 위치 차이 0, 자세 차이 0°(바닥 맞추기 회전 한 번만 다름).

## 놓침 · 루프 클로저

- 위치를 못 구한 장면은 상태 1 로 보내고 memmap 은 지도 · 물체에 넣지 않는다(개수는 결과 JSON `stream_lost`).
- 놓쳐도 지도는 하나다: 위치 추적이 마지막 위치(IMU 모드면 그 뒤 자이로 회전까지)에서 다시 시작하고, 그 구간 노드는 약한 연속 간선으로 이어진다. 루프가 예전 자리를 찾으면 자세 그래프가 그 구간을 통째로 옮긴다([slam.md](slam.md)).
- 루프 클로저로 노드가 움직이면 움직인 노드를 담은 그래프 블록이 오고, 그 뒤 장면은 보정된 좌표로 온다(상태 4).

### 루프 클로저 뒤 다시 쌓기(memmap)

- memmap 은 지도에 넣은 장면을 기준 노드와 그 노드에서 본 상대 위치로 보관한다(`kfstore.rs`). 상대 위치는 받을 때 `기준 노드 위치⁻¹ × 장면 위치` 로 구한다. 마지막 노드 위치 = 지도 보정 × 그 노드의 위치 추적 자세라, 이 값은 위치 추적 상대 움직임과 같고 루프 클로저로 바뀌지 않는다.
- **점유 지도·점 지도·물체·지나온 길**: 그래프 블록 뒤 노드가 마지막으로 쌓은 위치에서 2 cm 또는 2° 넘게 움직였으면(그 아래 보정은 모아 둠) `--rebuild-every` 초(기본 5)에 한 번까지 작업 스레드가 비우고 보관한 장면을 `지금 노드 위치 × 상대 위치` 로 처음부터 다시 쌓는다(실시간 장면과 같은 `map_frame`, 물체 병합 후처리는 15 장마다). 스트림이 끝났을 때 표시가 남아 있으면 한 번 더 쌓아 결과 지도·물체·`poses_map.txt` 가 끝난 그래프를 따른다. 물체 id 는 이어서 쓴다.
- 장면 보관은 줄인 형태: 깊이는 4 화소 간격, 검출 상자 안은 컬러·깊이 그대로(손실 없는 압축, 줄 안 차분 + LZ4), 장당 약 0.45 MB. 점유 지도는 16 화소 간격(8 + 16k) 깊이만 읽어 받은 값과 같고, 물체 점·사진은 상자 안만 읽는다. 사라짐 판정(보여야 할 자리의 깊이)만 4 화소 간격 깊이를 쓴다. 점 지도는 점 작업 스레드가 장면마다 남긴 점 격자(거른 뒤 `--scene-step` 간격의 깊이·색, LZ4)로 다시 쌓는다.
- 보관 예산 `--kf-store-mb`(기본 3000): 넘으면 보관한 장면을 하나 걸러 버리고 이후 두 배 간격으로 보관한다. `--rebuild-every 0` 은 끝에만 다시 쌓는다.
- 기준 노드를 모르는 장면(노드가 생기기 전, 다른 지도에서 끊긴 노드)은 받은 위치 그대로 쌓는다.

### 3D 점 지도(청크, memmap `chunks.rs`, 뷰어)

memmap 은 늘 점 지도를 만든다.

- **점 고르기**: 장면마다 `--scene-step`(기본 2) 화소 간격으로 깊이 점을 만들되 깊이 경계(5×5 에서 8 % 넘게 들쭉날쭉)와 비스듬히 본 면(이웃 ±2 화소로 만든 법선과 시선의 코사인 0.3 미만)을 빼고 `--pts-depth`(기본 3 m) 안만 쓴다.
- **누적(줄지 않음)**: 지도에 넣는 장면(물체가 들어가는 장면과 같은 장면 · 같은 자세)은 점도 반드시 넣는다(점 줄이 밀리면 점 격자 일부만, 많이 밀리면 기다림). 새 지도 · 다시 이어짐 · 다시 쌓기에도 점은 버리지 않는다. 새 점은 이미 점이 3 개 이상 든 세계 3 cm 칸(다른 청크 포함, 고친 자세 기준)이면 건너뛰어 빈 곳만 채우고, 자세를 고친 뒤에는 옮겨진 청크 점 가운데 앞 청크로 이미 찬 칸의 점만 뺀다(같은 곳을 두 번 돌아도 점 증가 fr1_desk 2 바퀴 +8.6 %).
- **청크**: 가까운 키프레임(기준 자세에서 0.6 m · 25° 안, 30 장까지)의 점을 한 청크에 그 기준 자세 좌표로 담는다. 청크는 그 안에 처음 든 보관 장면(닻)에 묶여, 닻의 고친 위치 × (닻에서 본 청크 자세)로 따라간다. 점 = i16 × 3(mm) + RGB u8 × 3(점당 9 바이트). 청크 안에서만 `--scene-vox` 칸으로 겹침을 거르고, 칸을 본 키프레임이 `--pts-obs`(기본 3) 장에 닿아야 점이 된다.
- **파일**: `chunks/<판>/c<id>.bin` = u32 n + n × i16 xyz + n × u8 rgb. 목록은 `view.json` 의 `scene_points.submap`(청크마다 id · 판 · 기준 자세).
- **루프 클로저 · 수평 맞춤**: 점을 다시 쌓지 않고 청크 기준 자세만 고친다(기준 키프레임의 고친 위치). 뷰어는 `/bstream` 칸 8 로 바뀐 청크 자세만 받는다.

- **뷰어로 넘기는 형식**(`/bstream`): 칸 8 = 바뀐 청크 자세(id · 판 · 점 수 · r00..r22 · px py pz, `view.json` 의 `scene_points.submap.list` 한 줄과 같은 순서), 점 파일은 판이 바뀐 청크만 다시 받는다(`chunks/<run>/c<id>.bin`). 겹친 점을 빼면 그 청크 판이 오른다.

검증(PC WSL, 사진 벡터 끔, 2026-11-19): fr1_desk 1 바퀴 점 818,632 → 313,889, 2 바퀴(같은 녹화를 이어 붙임) 1,618,481(+98 %) → 340,810(+8.6 %), fr3 long_office `--every 2` 2,698,999 → 629,154 점 · 23.2 → 8.4 MB, 최대 RSS 2,346 → 2,297 MB, 처리량 25.3 → 25.4 kf/s, 물체 수 같음.

## 시간

위치 프로그램(PC WSL, 최대 속도 재생): fr1 책상 268 장/초, 복도 232 장/초로 C++ 원본의 약 2.2 – 2.3 배. 본 스레드 계산은 장면당 2.8 – 3.1 ms(위치 추적 평균 2.6 – 2.9 ms)라 벽시계는 PNG 읽기 스레드가 정한다. 기록: [performance_log.md](performance_log.md) "Rust 위치 프로그램(slam_bridge) 통합 재검증".

C++ 원본 값([performance_log.md](performance_log.md) "연결 프로그램 시간"): PC 코어 하나에서 18 ms/장(그중 위치 추적 9.8 ms, TUM PNG 읽기 8 ms), 지도 갱신 1 초에 한 번 14 ms(최대 44 ms). 30 장/초 재생에서 위치 추적은 장면을 놓치지 않고, memmap 이 느리면 쓰기 큐에서 장면이 버려진다.

장면 넘기기(쓰기 스레드 0.8 ms/장 + memmap 읽기 스레드 0.5 ms/장)는 본 스레드 밖에서 돈다. 파이프 버퍼는 1 MB, 카메라가 준 RGB 사진은 그대로 쓰고, 큐에 든 장면은 저마다 제 버퍼를 가진다. memmap 은 사진·깊이를 받을 자리에 바로 읽는다.
