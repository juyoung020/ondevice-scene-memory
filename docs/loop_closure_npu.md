# 루프 클로저 · 재위치: MegaLoc(후보) + XFeat(검증)을 NPU 로

후보 찾기 = MegaLoc(168×224, DINOv2-B + SALAD), 검증 = XFeat(480×640) + 깊이 + 위쪽 방향 고정 4 자유도. 신경망 본체만 NPU(DX-M1, INT8 `.dxnn`), 그 앞뒤(전처리 · 집계 · 점 뽑기 · 기술자 · 짝 · RANSAC)는 모두 Rust. 런타임에 파이썬 없음. 앱에는 `--lc bow|net|both` 로 잇는다(기본 bow = RTAB-Map 낱말 루프 그대로, 7 절).

## 1. NPU 메모리 · 크기 (네 모델 함께 올릴 때)

| 모델 | 파일 | NPU 메모리(무게 + 명령 + 활성값) | NPU 작업 · CPU 작업 |
|---|---|---|---|
| ObjectSAM 분할 416·640 | 3.8 MB | 26.5 MB | 1 · 0 |
| SigLIP2 사진 | 132.1 MB | 137.2 MB | 1 · 0 |
| MegaLoc 168×224 | 120.5 MB | 132.2 MB | 1 · 0 |
| XFeat 480×640 | 1.0 MB | 44.6 MB | 1 · 0 |
| 넷 합 | 257.4 MB | 340.5 MB | |

`.dxnn` 머리(JSON)의 `rmap_info.size` 를 읽은 값(`dxinfo.py`). 보드 프로세스 쪽은 MegaLoc 투영 `megaloc_head_pca1024.bin` 68 MB 와 노드마다 약 87 KB(기술자 4 KB + XFeat 점 1,000 개의 i8 기술자 · 좌표 · 3D)가 더 든다(노드 1,000 개 ≈ 87 MB).

## 2. 결론

- 모델 둘 다 CPU 작업 없이 NPU 하나로 컴파일된다. MegaLoc 은 손질(큰 값 토큰 고정 · 자르기 · 회전 · GELU 나누기)과 DX-COM 2.4.1 의 자르기 꼴 우회(`10 − ReLU(10 − f)`)가 있어야 컴파일된다.
- Rust 앞뒤는 원본과 같다: 전처리 바이트 동일, 기술자 코사인 ≥ 0.9999998, Recall 같음. XFeat 후처리는 점 99.996 % 같은 자리, 검증 기하는 파이썬과 비트 동일.
- 8 비트로 찾는 성능은 거의 그대로(흉내 R@1 88.3 % ↔ 실수 89.0 %), 검증은 흐림 0 – 15 에서 XFeat 4 자유도(Rust 판)가 지금 BRIEF PnP 보다 성공률이 23 – 32 점 높다.
- 앱에 이어 TUM 7 녹화 · 흐림 · 합성 IMU 로 재 보니 ATE 는 낱말 루프와 같은 범위(차 0.2 cm 안)이고 지도에 들어가는 신경망 루프는 녹화마다 0 – 2 개다. 신경망 루프는 낱말 루프와 함께 늘 켜 둔다(옵션 없음, 모델이 없으면 시작하지 않음). 보드(NPU 시간 · 실제 녹화 ds_1118)에서 다시 잰다(9 절).

## 7. 앱 연결과 재생 결과

`ondevice slam` 은 RTAB-Map 낱말 루프와 신경망 루프를 함께 돌린다. 모델은 모델 폴더(`$ONDEVICE_MODELS`, 보드 `~/models`, PC `models/` · WSL `/mnt/c/ondevice/models`)의 `megaloc_168x224` · `megaloc_head_pca1024.bin` · `xfeat_480x640`(보드 `.dxnn`, PC `.onnx`)이고, 하나라도 없으면 시작하지 않는다. 아래 표의 bow · net 열은 연결할 때 비교한 기록(되돌릴 판: 태그 `lc-option`)이다.

흐름(`slam/src/lcnet.rs`, `app.rs` 의 `Engine::slam_process` · `lc_poll`, `loopclose.rs` 의 `NodeInput::lc_link`):
1. 지도 노드를 넘길 때 그 장면의 컬러 · 깊이(나눠 듦) · 위치 추적 자세 · 카메라를 일 번호로 맡겨 두고, 지도가 노드 id 를 정하면 루프 스레드("lc")로 보낸다.
2. 루프 스레드: MegaLoc 을 올려 두고 그동안 XFeat 전처리 → XFeat 올림 → MegaLoc 받아 집계 · 주성분 1,024 투영 → XFeat 받아 점 1,000 개 · 3D. 위쪽 방향 = 위치 추적 좌표의 z 를 카메라 좌표로(IMU 모드는 중력, 카메라 전용은 첫 장면 기준 위).
3. 후보 = 기술자 내적 상위 3 개(20 초보다 오래된 노드, 내적 ≥ 0.3) → XFeat 상호 최근접 짝 → 4 자유도 검증(맞은 점 ≥ 40) → 첫 성공을 루프로. 링크 = L · T · L⁻¹(L = 몸체 → 광학), 불확실성 = 0.3 m · 10° / √맞은 점(1 – 10 cm, 0.3 – 3°).
4. 다음 노드 단계에 낱말 루프 후보가 없으면 그 링크를 넣고 최적화 · 보정 크기 검사(원래 루프와 같은 문턱)를 거친다. 버려지면 링크도 지운다.
5. 노드의 기술자 · XFeat 점(i8 기술자 · 좌표 · 3D)을 표에 넣는다.

최대 속도 재생(`--tum … --rate 0`)은 결과를 한 노드 늦게 고정한다: 노드 단계마다 바로 앞에 보낸 노드 것만 빼고 모두 끝날 때까지 기다려 실행마다 같은 노드에 같은 링크가 들어간다(fr3 긴 사무실 · fr1 room 합성 IMU 두 번 실행 poses · final · stats 같음). 실시간은 끝난 결과를 바로 넘긴다.

## 8. 실행 빈도와 NPU 부하

노드는 `Rtabmap/DetectionRate=1` 이라 1 초에 1 개 안팎(fr1 25 – 45 개, 긴 사무실 85 개). 루프 스레드 시간(노드당, PC):

| 단계 | PC(ONNX 4 스레드, 9950X 코어 8 개에 묶음) |
|---|---|
| MegaLoc(전처리 + 신경망 + 집계 · 투영) | 78 – 84 ms(최대 120) |
| XFeat(전처리 + 신경망 + 점) | 11 ms |
| 짝 + 검증(후보 0 – 3 개) | 평균 0 – 5 ms, 최대 40 ms |

PC 최대 RSS 47 → 903 MB(MegaLoc 실수 ONNX 462 MB 를 ONNX Runtime 이 들고 있음). 위치 프로그램 지도 단계(`slam_ms`)는 한 노드 늦게 받는 덕에 5.5 – 7.6 → 6 – 29 ms. 물체 기억 한 프로세스에서 분할 대역(seg-cache)으로 장면을 아주 빨리 넣으면(fr1_desk 76.6 kf/s) PC CPU 의 MegaLoc 이 노드마다 260 ms 라 22.7 kf/s 로 묶인다 — PC 최대 속도 측정은 bow 로 잰다.

보드: NPU 두 모델 시간 · 네 모델 함께 올렸을 때 · 노드당 CPU 몫(집계 · 투영 · 점 · 짝 · 검증)은 9 절로 잰다.

## 9. 보드에서 할 일

## 10. 한계

- 입력은 640×480 컬러 + 맞춘 깊이(다른 크기 장면은 루프 스레드가 건너뜀).
- 카메라 전용 모드의 위쪽 방향은 첫 장면 기준이라, 위치 추적이 기울어 흐르면 4 자유도 가설이 덜 맞고 6 자유도 다듬기가 그 몫을 진다.
- 노드마다 약 87 KB 가 메모리 표에 쌓인다(노드 1,000 개 ≈ 87 MB).
- 질의와 20 초 안의 노드는 후보가 아니다(짧은 녹화 fr1 desk · desk2 는 후보가 0 개).
- 놓친 뒤 다시 잡기 · 지도 잇기는 지금 BRIEF 경로(`propose_merge`)가 맡는다.
- PC 는 MegaLoc 이 CPU 라 노드당 약 80 ms · 메모리 약 0.9 GB.
