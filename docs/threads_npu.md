# ondevice 스레드별 입력 · 출력과 NPU 호출

보드에서 `ondevice` 하나를 실행하면 아래 스레드가 한 프로세스 안에서 돈다. 숫자는 PC WSL(Ryzen 9 9950X, 코어 8 개 `taskset -c 16-23`) TUM fr1_desk 최대 속도 재생(`--slam "--tum … --rate 0 --block" --no-drop --surface --max-depth 3.5`)에서 잰 값이고,
NPU(DX-M1) 쪽 시간은 보드가 필요하다(아래 "보드 필요"). 측정은 실행 끝 요약 JSON 의 `scene_ms` · `seg_stage_ms` · `copies` · `waits` · `threads` · `viewer_wakes`(계측: `common::prof`).

## 1. 스레드별 입력 → 출력

| 스레드 | 코드 | 입력 | 하는 일 | 출력 |
|---|---|---|---|---|
| 카메라 읽기 | slam/src/io.rs | D435 USB 프레임 | 컬러 · 깊이 받기, 컬러에 맞춰 정렬 | 컬러 RGB 640×480 + 깊이 u16(버퍼 풀) |
| imu · imu-pose | slam/src/imu.rs | I2C 200 Hz | 거르기 · 시각, 장면 사이 회전 적분 | 링버퍼, 200 Hz 위치 → pose.json(메모리) |
| slam | slam/src/app.rs | 컬러 · 깊이 + IMU | 위치 추적 · 지도 그래프 · 루프 클로저 | 장면 스트림 → 메모리 큐(복사 없음) |
| reader | pipeline/src/main.rs `run` | 장면 스트림 | 위치를 바로 뷰어로, 분할 전처리(640 레터박스), **NPU 에 올리기** | 올린 장면(작업 번호) → seg-done |
| seg-done | main.rs `run` | 올린 장면 | **NPU 결과 기다리기**, 후처리(상위 300 · 마스크 해독) | 물체 목록 붙은 장면 → main |
| main | main.rs `run` | 장면 | 깊이 → 미터, 지도 · 물체 기억, 물체 사진 자르기 | 물체 기억, 사진 묶음 → embed, 점 장면 → pts |
| embed | pipeline/src/embed.rs | 물체 사진 묶음(Arc) | 전처리(32×32 조각), **NPU 에 K 장까지 함께 올리기 · 받기**, 정규화, 이름 | 사진 벡터(메모리 파일), 이름 |
| pts | main.rs `PtsWorker` | 깊이 · 컬러 + 위치 | 점 지도 넣기, 보관 장면 압축 | 점 지도 노드 → writer |
| rebuild | main.rs(필요할 때) | 보관 장면 + 바뀐 위치 | 루프 클로저 뒤 다시 쌓기 | 새 지도 · 물체 |
| view | main.rs `ViewWorker` | 물체 JSON · 격자 | 방 나누기, view 판 | view 판(메모리) |
| writer | pipeline/src/out.rs | 쓸 파일(PNG · PLY · 점 노드) | 짜기, 메모리 파일로 걸기, 줄이 빌 때 뷰어 한 번 깨움 | 메모리 기억 폴더 |
| save | main.rs `saver` | 저장 버튼 · `--save-every` | 메모리 기억 폴더를 디스크에(신호가 올 때만 깸) | 디스크 기억 폴더 |
| sgview-stream · http | viewer/sgview | 메모리 파일 · view 판 | 바뀐 몫만 브라우저로 | 브라우저 |

분할 길의 스레드: 전 reader · seg-infer · seg-post(`--npu-jobs` 2 이상이면 + seg-collect) **3 – 4 개 → 후 reader · seg-done 2 개**.
전처리(0.15 – 0.21 ms)와 후처리(0.44 – 0.52 ms)는 장면마다 1 ms 도 안 돼, 이것만 하는 스레드는 깨우는 비용만 들었다. 지금은 올리기를 전처리한 스레드가 바로 하고,
결과를 기다린 스레드가 그대로 후처리까지 해 본 스레드에 넘긴다. PC ONNX 판은 실행 스레드 `seg-onnx` 하나가 NPU 자리를 대신한다(보드에는 없음).

## 2. NPU 호출

### ObjectSAM(분할) — 장면마다

| 단계 | 스레드 | 내용 | 데이터 · 시간(PC ONNX, fr1_desk 123 장) |
|---|---|---|---|
| 전처리 | reader | 640 레터박스(회색 띠는 처음 한 번), NPU 입력 버퍼(u8 NHWC)에 바로 | 0.88 MB/장(띠 뺀 몫), 0.15 ms |
| 올리기 | reader | `dxrt_engine_run_async(e, 입력, NULL, 출력 버퍼, &id)`: **받을 버퍼를 올릴 때 넘김** | 0.33 ms(PC: f32 NCHW 변환 4.7 MB 포함) |
| 함께 올리기 | reader | 자리(`--npu-jobs K`, 보드 기본 1)가 날 때까지 기다렸다 올림 | |
| 받기 | seg-done | `dxrt_engine_wait(e, id, NULL)`: 결과는 이미 받을 버퍼에, **DXRT 가 다시 복사하지 않음** | 출력 3.3 MB/장 복사 0 번 |
| 후처리 | seg-done | `heads_to_det`(문턱 · 상위 300), `decode`(계수 × 원형 → 마스크) | 0.44 ms |
| NPU | — | 모델만 9 ms, 실행 중 지연 25 ms 가운데 약 10 ms 는 DXRT 가 원형(32×160×160)을 실수로 바꾸는 몫 | 보드 필요 |

DXRT 3.4.0 확인(libdxrt.so 디스어셈블): `dxrt_engine_wait` 는 출력 포인터가 있으면 텐서마다 `memcpy`, NULL 이면 건너뛴다. `dxrt_engine_run_async` 는 출력 포인터(4 번째 인자)를 그대로 `RunAsync` 에 넘긴다.
전에는 올릴 때 NULL · 받을 때 우리 버퍼라 `--npu-jobs` 2 이상에서 장면마다 3.3 MB 를 한 번 더 복사했다(한 장씩 동기 `run` 은 처음부터 우리 버퍼에 바로).

### SigLIP2(사진 벡터) — 물체가 새로 · 더 크게 보일 때

| 단계 | 스레드 | 내용 | 데이터 · 시간 |
|---|---|---|---|
| 묶음 받기 | embed | 한 기록 회차(write_view)에 바뀐 사진을 **한 묶음으로 한 번** 받음(전: 사진마다 보냄) | fr1_desk 121 장 → 묶음 6 개, 가장 큰 묶음 46 |
| 전처리 | embed | 묶음의 처음 K 장은 rayon 으로 함께, 뒤로는 한 장 받을 때마다 그 자리에 한 장 | 768 KB/장(f32 조각 64 × 3,072), PC 0.4 – 0.7 ms |
| 올리기 · 받기 | embed | **K 장까지 함께**(`--embed-jobs K`, 기본 3 = NPU 코어 수, DXRT 버퍼도 K 벌), 결과는 받을 버퍼에 바로 | 출력 3 KB 복사 0 번 |
| 후처리 | embed | 정규화, 이 물체를 본 사진 모두의 평균 방향을 검색 줄(벡터 파일)로, 메모리 기억 폴더(`--serve`)면 메모리 파일로만(전: 장마다 SD 카드에 쓰고 이름 바꿈), 이름 · 구조물 고르기(낱말 104 개, 34.6 µs/물체) | |
| NPU | — | 모델만 13.5 ms. K = 3 · 4 · 6 · 8 처리량, 분할과 함께 돌 때 서로 막는지 | 보드 필요 |

벡터는 같은 사진이면 같은 값: 실행 끝 물체 24 개의 `O*_rgb.png` 로 다시 계산한 벡터와 `O*_emb.bin` 코사인 평균 · 최소 1.0000(`ondevice --embed-check`, 전 · 후 판 모두).

## 10. 보드 필요

- 분할: K = 1 · 2 · 4 에서 올리기 · 받기 기다림 · 장면 지연, 출력 복사 없앤 효과(3.3 MB/장), CPU 사용률, kf/s.
- 사진 벡터: `--embed-jobs` 3 · 4 · 6 · 8 처리량(더 오르지 않는 곳을 기본값으로), 분할과 함께 돌 때 서로 막는지(코어 배정 `--seg-npu` · `--embed-npu`).
- 배치 차원 사진 벡터 모델(입력 [N, 64, 3,072], N = 4 · 8)과 동시 올리기 비교.

## 11. 검색: 물체 벡터 메모리 표(`viewer/sgview/src/objtable.rs`)와 한 단계 검색

검색은 한 단계다(근거 · 정확도 비교는 [search_direct.md](search_direct.md)): 검색어 글 벡터 × 물체 사진 벡터 표 → p = sigmoid(111.83 · cos − 16.766876) →
p ≥ 0.004(한글이 든 검색어 0.0025)인 물체를 코사인 순으로, 물체 이름 글자가 검색어와 겹치면 맨 앞(점수 1). 단어장 · NULLS · 이름 몫은 쓰지 않는다
(그 판은 태그 `search-vocab-last`). 물체 사진 벡터는 메모리 표 하나에 두고 벡터 파일이 바뀐 물체만 다시 넣는다(질의 때 파일을 읽지 않음).

| 공개 함수 | 하는 일 |
|---|---|
| `ObjTable::new(dim)` | 빈 표 |
| `upsert(key, &v)` · `remove(&key)` | 물체 추가 · 갱신 · 삭제(삭제는 마지막 줄을 그 자리로) |
| `sync_bytes(&[(key, 파일 바이트)])` | 벡터 파일 바이트로 맞추기: 바뀐 것만 다시 넣고 목록에 없는 물체는 지움 |
| `row` · `vector` | 줄 번호, 그 줄의 벡터 |
| `scores(&q)` · `top_k(&q, k)` | 질의 벡터와 모든 물체의 내적, 큰 순 k 개 |

```rust
let mut t: sgview::objtable::ObjTable<u32> = ObjTable::new(768);
t.upsert(7, &picture_vector);           // 추가 · 갱신
let best = t.top_k(&query_vector, 5);   // [(물체 번호, 내적)] 큰 순
t.remove(&7);
```

내적은 `objtable::dot`: 보드(aarch64)는 NEON 4 칸 × 4 묶음, PC 는 차례대로 더함(보드는 차례대로 더한 값과 상대 1e-7 안팎 차). 128 줄 아래는 한 스레드, 위는 rayon.

질의 한 번(PC WSL, 질의 글 벡터는 이미 있음, 벡터 파일은 메모리(`--serve`), 5 번 평균, 다른 세션이 코어를 쓰던 때라 흔들림):

| 물체 수 | 전(질의마다 파일 읽기 + 물체 × 단어장 1,230 내적 + softmax) | 후(메모리 표 + sigmoid) | 벡터가 모두 새로 들어온 뒤 첫 질의 |
|---|---|---|---|
| 10 | 4.8 – 6.3 ms | 0.004 – 0.009 ms | 2.5 ms |
| 100 | 43 – 56 ms | 0.08 ms | 0.4 ms |
| 1,000 | 419 – 578 ms | 0.27 – 1.5 ms | 5.5 ms |

질의 글 인코더(검색어마다 한 번)는 PC ONNX 30 – 34 ms, 보드 Rust 약 75 ms 라 이제 검색 시간의 거의 전부다(`--vocab vocab/names.voc` 에 든 낱말이면 건너뜀).

PC 끝까지 확인(fr1_desk, 물체 24 개, `ondevice view … --search-model`): "monitor" → 이름 글자로 모니터 4 개, "모니터" → 사진으로 모니터 3 개(p 0.083 · 0.048 · 0.004), "고양이" · "umbrella" → 없음.

지도 이름표는 그대로 실내 낱말 104 개(`vocab/indoor.voc`)에서 가장 닮은 것(물체 하나 34.6 µs). 벽 · 바닥 · 천장 판정은 구조물 8 낱말 표(`vocab/structural.voc`, `--structural`): 가장 닮은 낱말이 floor · wall · ceiling · baseboard 이고 p ≥ 0.003 이면 구조물, 천장은 기억에서 뺀다(fr1_desk 물체 24 개 중 5 개를 구조물로).

- 끝(최대 RSS 3.5 GB, 끝 다시 쌓기 포함): 보관 장면 1,227 개 1,179 MB(장면당 0.96 MB, 압축한 컬러 + 깊이) · 점 지도 90 MB(점당 약 52 바이트) · 메모리 기억 폴더 36 MB(물체 파일 17 MB · 점 지도 노드 17 MB). 나머지 약 1 GB 는 PC ONNX 모델 · 다시 쌓기 중간 상태.
- 시간에 따라 늘어나는 몫의 대부분(약 70 %)이 다시 쌓기용 보관 장면이다. 보관은 예산(`--kf-store-mb`, 기본 남은 메모리의 15 %: 보드 8 GB 에서 약 1 GB)을 넘으면 하나 걸러 버려 끝없이 늘지는 않지만 그 예산까지는 찬다.
- 줄일 차례(효과 큰 순): ① 보관 장면을 컬러 · 깊이 원본 대신 그 장면의 점(기준점 + 상대 좌표 정수 + 축소 색)과 물체 마스크 안 깊이만으로 — 장면당 0.96 MB 의 대부분, 다시 쌓기 결과가 바뀌므로 비교가 필요 ② 점 지도 점당 52 → 약 8 바이트(덩어리 기준점 + i16 mm · RGB565) ③ 물체 사진은 사진 벡터를 낸 뒤 작은 미리보기만(물체 파일 17 MB 와 물체마다 들고 있는 원본 사진). ③ 은 물체 기억(`maps.rs`)의 사진 비교와 엮여 그쪽 구조 개편과 함께 한다.

보관 장면 줄이기 ①(검출 상자 합집합, 결과 같음): 줄인 보관은 검출 상자마다 컬러 · 깊이를 따로 압축해 겹친 상자의 화소를 여러 번 들고 있었다. 이제 상자들의 합집합을 줄마다 겹치지 않는 구간으로 만들어 그 화소만 한 번 보관한다(구간은 보관한 검출 상자에서 다시 만들어 따로 저장하지 않음). 다시 쌓기가 읽는 컬러 · 깊이는 전과 화소까지 같다.
