# 속도 개선 기록 (발표용)

같은 입력으로 잰 처리 속도의 변화. 입력은 TUM RGB-D fr3/long_office_household(87 초, 2,585 프레임 → 5 프레임마다 키프레임, 516 개), 깊이는 Kinect 실측, 분할은 YOLO26s-seg(COCO).
"키프레임 시간" = 한 키프레임을 읽어서 분할하고 지도·물체 기억에 반영하고 기록까지 하는 데 드는 시간.

## 무엇을 바꿨나

### ①→② 같은 일을 묶어서 (파이썬)
- 물체마다 SigLIP 을 따로 부르던 것을 한 장면의 물체를 한 번에(배치) — GPU 호출 수가 물체 수 → 1.
- 물체 점 정리(지지 칸 골라내기)를 관측마다 하지 않고 기록할 때만.

### ③→④ 다시 계산하지 않고 쌓기 (Rust 로 다시 짬)
- 파이썬은 3D 지도를 쓸 때마다 지금까지의 점 **수백만 개를 다시 정렬**해서 칸으로 묶었다 → 시간이 쌓인 점 수에 비례해 계속 늘었다.
- Rust 판은 1 cm 칸 **해시 표에 새 점만 더하고**(같은 키프레임은 칸당 한 번 셈), 쓸 때는 칸을 한 번 훑기만 한다 → 키프레임 시간이 지도 크기와 거의 무관.
- 물체 트래커·점유 지도도 같은 방식(굵은 칸 겹침으로 같은 물체 판정, 2D 칸은 키프레임당 한 번).
- 결과: 지도·물체·기록 시간 **1,100 ms → 17 ms(PC) / 36 ms(Pi)**.

| 단계별 (ms/키프레임) | 읽기 | 분할 | 지도 | 물체 | 기록 | 합 |
|---|---|---|---|---|---|---|
| ④ PC 순서대로 | 4 | 65 | 7 | 2 | 8 | 85 |
| ⑥ Pi 순서대로 | 6 | 70 (NPU 54) | 9 | 4 | 24 | 113 |

### ④→⑤, ⑥→⑦ 분할과 지도를 겹치기
- 분할(NPU/모델)이 도는 동안 CPU 는 놀고, CPU 가 지도를 만드는 동안 NPU 가 놀았다.
- 작업 스레드가 다음 장면의 읽기·분할을 한 장 앞서 돌리게 했다 → 키프레임 시간 ≈ max(읽기+분할, 지도+물체+기록).
- 결과는 똑같다(물체 수·점 수 동일), 처리량만 오름.

### ⑨→⑩ 비동기 구조와 캐시
- **NPU 동시 실행(되돌림)**: 깊이·분할·SuperPoint 를 스레드 3 개로 동시에 던지면 읽기+NPU 161 ms → 88 ms 였지만, 실시간으로 몇 분 돌리자 DX-M1 DMA 쓰기 오류(errno -70) → PCIe 링크 다운 → 재부팅 필요. 지금은 차례대로. 다음: DXRT 비동기 API(`dxrt_engine_run_async`)를 한 스레드에서 쓰는 방식으로 다시 시도.
- **한 번만 계산**: 이전 장면 특징점·기술자를 캐시하고, 짝 맞추기(400×400×256 내적, 8 갈래 SIMD)를 장면당 1 번만 해 포즈·배율이 같이 씀.
- **위치표 캐시**: 깊이 모델 입력 768² 로 늘리기·결과 되돌리기의 화소 위치·가중을 처음 한 번만 계산.
- **기록 스레드**: 실시간 모드에서 PLY·PNG·view.json 쓰기를 별도 스레드가 순서대로(본 흐름은 바이트만 넘김).
- 구조: [작업 스레드: 읽기 → NPU 3 개 동시] → [본 스레드: 포즈·배율 → 지도·트래커 누적] → [기록 스레드: 파일].

## 다음 개선 거리
- 점 지도에 점 넣기(`SceneMap::add`): 점 스레드 장면당 7.2–7.6 ms, 다시 쌓기의 약 70 % 로 작업 스레드에서 가장 큰 몫. 표준 해시맵 두 장(뜨거운 칸·식은 칸) 조회가 대부분이라, 미리 읽기(prefetch)가 되는 열린 주소 표로 바꾸면 점·다시 쌓기 CPU(코어 2 개 흉내에서 합 약 80 CPU 초)가 함께 준다.
- 본 스레드에 남은 긴 멈춤(PC 시간): 깊이 쌓기 최대 20–28 ms(평균 4.5 ms), 다시 쌓기 결과 넣기 11–23 ms, 물체 병합 13–17 ms → 여러 장면에 나누기.
- 방·엣지: 점유 지도가 크게 바뀔 때만 다시 계산(지금은 기록할 때마다, view.json 기록 한 번에 1–1.5 ms).
- 3D 지도 파일: 바뀐 칸만 덧붙이는 형식(지금은 몇 장면마다 전체).
- Pi 깊이: 영상을 768² 로 늘리고 결과를 되돌리는 CPU 작업이 키프레임당 약 50 ms → 정수 연산·NEON 또는 NPU 쪽 크기 맞춤으로.
- Pi: 분할 키프레임당 97 ms 를 보드에서 단계별로 나눠 재기(`분할 단계 평균 ms` 줄, `--seg-check`). PC 에서 전처리 + 마스크 해독은 합쳐 0.14 ms(3 배 해도 0.4 ms)라 남는 몫은 추론 호출(`dxrt_engine_run`) 안: NPU 54 ms 밖의 입력·출력 옮기기가 크면 그쪽을 줄이기.
- 깊이도 NPU(YOLO26s-depth, 41 ms/장)로 — 분할과 같은 장면을 두 모델로, 또는 합친 모델 하나로(계획 중).
- 목표: Pi 키프레임 ≥ 15 Hz.

측정 방법: `pipeline/target/release/memmap` 이 25 키프레임마다 단계별 평균 ms 와 kf/s 를 찍고, 끝에 JSON 으로 요약한다.

- **등속 예측 + 움직임 검사**: 직전 속도로 다음 위치를 예측해 초기값으로 쓰고, 2 m/s·180°/s 를 넘는 결과는 버리고 예측을 씀.

## 데스크톱 최적화 (2026-11-04 밤, 보드는 꺼 둠)

**표면 지도 품질 재기**: `surfcmp <A> <B>` — A 면의 꼭짓점마다 B 면까지 거리(정확도), 반대 방향(완전도). 기준 B = Kinect 실측 깊이 표면, A = 딥러닝 깊이 표면(정답 위치).

| TSDF 가중 | 책상 정확도 / 완전도(10 cm) | 사무실 정확도 / 완전도 | F(책상 / 사무실) |
|---|---|---|---|
| 균일(채택) | 0.376 / 0.431 | 0.209 / 0.327 | **0.40 / 0.26** |
| 1/거리² | 0.473 / 0.217 | 0.327 / 0.155 | 0.30 / 0.21 |
| 1.5 m 기준 1/거리² | 0.437 / 0.295 | 0.282 / 0.220 | 0.35 / 0.25 |

거리 가중은 먼 면을 덜 만들 뿐 → 균일 유지. 정답 위치에서 깊이 배율은 이미 0.94–0.96 으로 맞춰지므로 남은 오차는 깊이 모델의 모양 오차.

**SuperPoint 간격(`--sp-every N`, 사이 장면은 RGB-D 직접 방식)**: 느린 영상(사무실, Kinect)은 3 장마다여도 0.129 → 0.124 m 로 그대로, 빠른 영상(책상)은 0.11 → 0.53 m 로 나빠짐. 보드 시연(사무실)은 2–3 장마다로 NPU 작업을 줄인다.
**직접 방식(DVO) 강화**: 5 단계 피라미드 + 시작값 둘(움직임 없음 / 직전 움직임, 밝기 오차가 0.05 넘으면 둘째도 풀어 나은 쪽).

| 설정 | 책상 Kinect | 사무실 Kinect | 책상 딥러닝 | 사무실 딥러닝 |
|---|---|---|---|---|
| 4 단계, 시작값 하나 | 0.333 m(실패 13) | 0.542 m | 0.598 m | 1.266 m |
| **5 단계 + 시작값 둘** | **0.092 m(0)** | **0.224 m** | 0.601 m(0) | 1.368 m |

이걸로 SuperPoint 2 장마다(`--sp-every 2`)가 매 장보다 낫거나 같음: 책상 Kinect 0.113 → 0.082 m, 사무실 0.129 → 0.119 m, 책상 딥러닝 0.567 → 0.533 m(사무실 딥러닝만 1.034 → 1.105 m). 웹캠 녹화(직접 방식) 실패 117 → 91 장.
- 직접 방식에서 딥러닝 깊이일 때 640×480 단계 생략: 정확도 같음(책상 0.601 → 0.608 m, 사무실 1.368 → 1.307 m), 위치 추정 36 → 21 ms(PC). 실제 깊이(Kinect)는 고운 단계가 도움 돼 유지.
**지도 품질로 본 위치 추정(정답 위치 표면과 5 cm 안 F, Kinect 깊이)**: 책상 — 매 장 SuperPoint 0.543 · 2 장마다 **0.728** · 직접 방식 0.496 / 사무실 — 0.697 · 0.610 · **0.773**. 위치 오차(ATE)가 작다고 지도가 늘 더 맞지는 않음(사무실은 직접 방식이 ATE 는 크지만 지도는 가장 맞음).

**방 쪼개짐**: 빈칸의 작은 미관측 구멍을 닫힘(2 칸)으로 메우고, 맞닿은 경계가 1.2 m 넘는 방끼리 합침 → 사무실(정답 위치) 방 3 → 1 개(65 m², 물체 35), 카메라만으로 위치일 때 2 개(위치 오차로 생긴 8 m² 조각).

- 직접 방식의 가우스-뉴턴 합산을 코어 4 개로 나눔(점 4000 개 이상 단계만): 위치 추정 22 → 19 ms(책상 Kinect), 16 → 12 ms(사무실 딥러닝), PC. 시험: 기준 장면(keyframe)에 맞추기·거친 단계에서 시작값 고르기 → 책상 위치 오차 0.1 → 0.2–0.5 m 라 앞 장면에 맞추는 방식 유지.
- 물체 마스크 해독: 계수·원형 내적을 원형 격자(160²)에서 먼저 하고 화소마다 쌍선형으로 읽음(선형이라 같은 값, 결과 물체 49 개 그대로) → 분할 단계 14 → 8 ms(PC, 사무실), 53 → 68 장/초. 보드는 분할 70 ms 중 CPU 해독 16 ms 몫이 줄어듦.
- 지도·물체·표면 칸 표의 해시를 기본 SipHash → 정수 열쇠용 빠른 해시(Fx 곱셈 + 마지막 비트 섞기)로: 점 지도 지도 9 → 6 ms·기록 5 → 3 ms, 65 → 87 장/초(PC, 사무실 Kinect, 결과 같음). 마지막 섞기 없이 곱셈만이면 높은 비트만 다른 칸이 한 통에 몰려 지도 99 ms 로 느려짐.

- 표면 지도 모드에서 점 지도용 3D 점 목록을 건너뜀: 지도 단계 3 → 1 ms, 96 → 100 장/초(PC).
- 실시간 기록(0.4 초마다) 중 물체 점 갱신: 중앙값·분위수를 정렬 6 번 → 선택(select_nth, 같은 값)으로 평균 4.1 → 1.0 ms, 최대 27 → 6.6 ms. 물체 사진 PNG 압축은 기록 스레드로.

- 녹화를 최대 속도로 돌릴 때 `--fast-pose` 는 `--depth-every` 장마다 깊이를 기다려 맡김(결과가 매번 같게).
- 잠깐 잡힌 잘못된 검출 지우기(두 번 이하로 보였고 3 초 넘게 다시 안 보임): 사무실 딥러닝 깊이 물체 86 → 67 개, Kinect 49 → 36, 책상 30 → 21(정답 위치).

- 시험: 수평면 법선으로 기울기를 조금씩 바로잡기(중력처럼, 이득 0.1·0.3) → 모든 경우 나빠짐(책상 0.26 → 0.37–0.39 m, 사무실 0.88 → 0.99–1.16 m) → 보류.
- 피라미드 기울기 영상은 추적에 쓰는 단계(딥러닝 깊이는 320×240 부터)만: 위치만 추적 장면 5.5 → 4.5 ms(PC, 결과 같음).
- 뷰어: 3D 지도 조각 32 개마다 한 덩어리로 합침(그리기 호출 35 → 4, 점 243 만 개 그대로). 실시간은 조각이 1 초마다 나오므로 10 분 시연에서도 그리기 호출 약 50 개.
- 시험: 밝기 차이 가중을 후버 → t 분포(ν=5, 척도 반복마다) → 대부분 조금 나빠짐(책상 0.26 → 0.30 m, 사무실 빠른 조건 0.56 → 0.75 m) → 후버 유지.
- 직접 방식 두 번째 시작값(직전 움직임)은 실패·불가능한 움직임일 때만(밝기 오차 0.05 초과로는 안 풂): 사무실 15 장 간격 1.16 → 0.91 m, 5 장 0.88 → 0.86 m, 책상 6 장 0.51 → 0.49 m, 웹캠 녹화 실패 84 → 82, 조금 빠름.
- `--fast-pose` 기준 장면은 5 cm·3° 넘게 움직였을 때만 바꿈(천천히 움직이면 같은 기준을 오래): 사무실 0.86 → 0.64 m, 3 장 간격 1.03 → 0.78 m, Kinect 0.23 → 0.18 m, 책상 0.26 → 0.30 m.
- `--fast-pose` 수정: 위치 기록 없이 늦게 온 깊이 장면은 기준 자세에서 이어 풀고 최신 추적 상태를 되돌려 둠(시작 직후 시간이 거꾸로 섞이던 것).
- 녹화 최대 속도 재생의 `--fast-pose` 는 모델을 작업 스레드에서 차례대로: 모델 스레드로 돌리면 위치 추적 때 직전 장면 깊이가 아직 없어 두 장 전에 맞추게 돼 실패 132 회(기존 82) → 차례대로 83 회. 실시간 카메라는 깊이가 늦게 오는 게 실제 조건이라 모델 스레드 그대로(보드에서 fasttest 로 비교).

## 뷰어 표면 지도 묶어 그리기 (2026-11-05)

## 보드 흉내(코어 4 개)에서 실측 깊이 + 외부 SLAM 위치 + 표면 지도 경로 (2026-11-05)

## D455 깊이→컬러 정렬 (2026-11-05)

`bridge/align` 의 fast_align(rs2::align 과 같은 규칙·같은 float 연산 순서)과 librealsense v2.59.1 정렬 비교. "이식" = librealsense 코드를 시험 쪽에 옮긴 것(프레임 할당 없는 계산부), "실제" = 이 PC 의 SDK 2.59.1 `rs2::align.process`(software_device, 120 장). 방법과 확인 순서: [`realsense_input.md`](realsense_input.md).

- 같은 코드를 GCC(x86-64 SSE2, WSL)로 빌드하면 640×480 한 스레드가 0.79 ms 로 옮겨 온 SSE 경로(0.58 ms, SSSE3)보다 느리다. SSE4.1 을 켜면 0.69–0.71 ms, AVX2 0.42–0.47 ms. 차이는 SSE2 에 없는 32 비트 곱·고르기를 흉내 내는 비용.

- aarch64 계산 루프(llvm-mca, Neoverse-N1 모형): SDK NEON 7.26 주기/화소, fast_align 7.52, 빠른 식 6.64. 흩뿌리기는 둘 다 스칼라.
- 시험: 줄마다 깊이를 float 로 바꾸는 별도 루프(MSVC 가 u16 이 섞인 루프를 벡터화하지 못함), 정수 변환 범위 묶기를 삼항식으로(std::min/max 는 MSVC 가 벡터화 못 함), 모서리 하나 경우 화소 번호와 화면 밖 판정을 벡터 루프에서(부호 비트로 분기 없이) → MSVC 한 스레드 1.50 → 0.61 ms.
- Pi 5 환산(A76 = PC 코어의 2–3 배 시간 가정): rs2::align NEON 640×480 1.8–2.8 ms, fast_align 한 스레드 1.2–2.1 ms, 스레드 4 개 0.6–0.9 ms, 일반 구현 13–20 ms. 보드 실측 전.

## 물체 분할 단계: 전·후처리 줄이기, 전처리 → 추론 → 후처리 겹치기 (2026-11-10, main 3b15d5a 위)

스트림 입력의 분할을 세 단계로 나눔: 전처리(레터박스, 읽기 스레드) → 추론(모델 호출, `infer` 스레드 하나가 차례로) → 후처리(마스크 해독, 후처리 스레드). 장면을 한 장씩 차례로 넘겨 순서는 그대로이고, 추론이 도는 동안 앞 장면의 후처리와 다음 장면의 읽기·깊이 변환·전처리가 겹친다(`--seg-pipe off` = 셋을 읽기 스레드에서 차례로). 다음 장면은 앞 장면을 본 스레드가 받아 간 뒤, 추론이 끝날 무렵에 맞춰 골라 묵은 장면이 쌓이지 않는다.

- 틀린 위치를 지도에 넣지 않으므로 오차가 준다. 대신 놓침으로 보내는 장면이 는다: 처음 보는 곳에서 다시 시작하면 아는 곳을 다시 볼 때까지 지도가 멈춘다(large_loop_1 은 한 바퀴를 다 돌아 1413 번째 장면에서 이어짐).
- 흔드는 영상에서는 같은 지도에서 바로 다시 잡는다(camera_shake_1 에서 5 번). 다시 잡기는 놓친 장면에서만 돌고 한 번에 10–35 ms.
- TUM fr1 영상 가운데를 뺀 재생(10 % 또는 3 %)은 모두 다시 이어졌다: desk2 7 · 183 장 뒤, 360 은 159 · 63 장 뒤, room 287 · 111 장 뒤, floor 약 474 · 315 장 뒤, rpy 는 새 지도 없이 같은 지도에서 바로.
- `Vis/MaxFeatures 800` 은 놓침을 줄인다(sofa_shake 336 → 57, camera_shake_1 155 → 79). 데스크톱에서 장면당 2–4 ms 더 든다.

### 놓친 뒤 멈춤 줄이기: 새 지도의 장면을 맡아 두었다 잇기 (데스크톱 WSL, 2026-11-12)

놓친 뒤 새 지도에서 찍은 장면을 버리지 않고 맡아 두었다가 믿는 지도와 이어지면 넣는다([`bridge.md`](bridge.md) "맡아 두기"). ETH3D 영상, `rtab_bridge --tum | memmap --stream - --depth kinect --seg yolo26s-seg.onnx --every 2 --max-depth 3.5 --no-drop`. 연결 프로그램 칸은 모든 장면 기준, memmap 칸은 받은 장면 2 장마다 기준. 오차는 지도에 넣은 장면 위치(`poses_map.txt`)의 정답 대비 오차이고 "전"은 맡아 둔 장면 없이 넣던 장면만의 값(같은 실행의 `poses_est.txt`).

| 영상 | 연결 프로그램: 놓침 → 그 가운데 맡김 → 이어짐 | memmap: 맡아 둠 → 지도에 들어감 | 오차 전 → 후 |
|---|---|---|---|
| kidnap_1(884 장) | 595 → 552 → 440 | 276 → 220 | 0.044 → 0.019 m |
| large_loop_1(1511 장) | 1068 → 909 → 483 | 453 → 241 | 0.153 → 0.188 m |
| sofa_shake(500 장) | 405 → 258 → 0 | 128 → 0 | 0.035 m 그대로 |
| camera_shake_2(871 장) | 782 → 384 → 0 | 193 → 0 | 0.034 m 그대로 |
| camera_shake_1(318 장) | 173 → 0 → 0 | 0 | 0.018 m 그대로 |

- 카메라를 옮긴 영상(kidnap_1)과 큰 한 바퀴(large_loop_1)에서 놓침으로 버리던 장면의 74 % · 45 % 가 지도에 들어간다. kidnap_1 은 지도에 넣는 장면이 144 → 364 장으로 늘고 오차도 준다. large_loop_1 은 223 → 464 장으로 늘고, 이어진 구간이 루프 클로저 하나로만 묶여 오차가 3.5 cm 는다.
- 흔드는 영상은 새 지도가 짧게 끊겨 믿는 지도와 이어지지 않는다. 맡아 둔 장면은 지도에 들어가지 않아 결과가 그대로다(보관 메모리만 씀: sofa_shake 159 장 193 MB, `--kf-store-mb` 예산 안).
- 흔드는 영상의 놓침 수는 실행마다 다르다(sofa_shake 246–407, camera_shake_2 559–782).

### 장면 넘기기: 연결 프로그램 → memmap 복사 줄이기 (데스크톱 WSL, 2026-11-11)

TUM fr1 desk2 640 장(640×480, 장면 하나 1.54 MB), `rtab_bridge --out - | memmap --stream - --every 100000 --no-drop`, 3 번씩.

장면 하나에 드는 시간(전, 계산과 넘기기를 나눔):

| 곳 | 일 | ms/장 |
|---|---|---|
| 연결 프로그램 본 스레드 | 위치 추적(계산) | 9.4 |
| 연결 프로그램 본 스레드 | PNG 읽기(재생에서만) | 6.9 |
| 연결 프로그램 본 스레드 | 쓰기 큐에 넣기 | 0.02 |
| 쓰기 스레드 | BGR → RGB + 파이프 쓰기(넘기기) | 2.0 |
| memmap 읽기 스레드 | 파이프 읽기 + 복사(넘기기) | 0.92 |
| memmap | 분할(계산, CPU) | 65 |

넘기기 전·후:

| | 전 | 후 |
|---|---|---|
| 쓰기 스레드 ms/장 (평균 / 중앙) | 2.0 / 1.73 | 0.8 / 0.56 |
| memmap 읽기 스레드 CPU ms/장 | 0.92 | 0.48 |
| 장면당 통째 복사(읽는 쪽) | 버퍼 → 사진, 버퍼 → 임시 → 깊이 | 받을 자리에 바로 |
| 파이프 한 번에 넘기는 크기 | 64 kB | 1 MB |

- 바꾼 것: 파이프 버퍼 1 MB, 읽기 버퍼를 머리·그래프용 64 kB 로 줄여 사진·깊이를 받을 자리에 바로 읽기, 카메라가 RGB 로 준 사진은 바꾸지 않고 그대로 쓰기(전에는 RGB → BGR → RGB).
- 값은 같다: 같은 영상에서 옛·새 연결 프로그램의 스트림이 바이트 단위로 같고, 같은 스트림 300 장을 옛·새 memmap 에 넣어 나온 파일 468 개 가운데 466 개가 바이트 단위로 같다(나머지 `view.json`·`octree.json` 은 같은 프로그램을 두 번 돌려도 달라지는 파일).
- 넘기기는 본 스레드 밖에서 돌고 장면당 3 ms → 1.3 ms. 한 장면 시간의 대부분은 분할과 위치 추적이다.

### 다시 쌓기용 장면 보관: 압축 준비 줄이기 (데스크톱 WSL, 2026-11-11)

TUM fr1 desk2 실시간 재생(`rtab_bridge --rate 1 --out - | memmap --stream -`, 기본 옵션)에서 memmap 본 스레드가 장면마다 쓰는 시간은 중앙 4.4 ms 이고, 그 가운데 분할 밖에서 가장 큰 것이 보관할 장면의 압축이다.

| 곳 | 일 | ms/장 |
|---|---|---|
| memmap 본 스레드 | 보관할 장면 압축(컬러 + 깊이) | 1.9 ~ 2.2 |
| memmap 본 스레드 | 점 지도 스레드로 넘길 사진·깊이 복사 | 0.2 ~ 0.4 |
| memmap 본 스레드 | 물체 갱신 | 0.8 |

압축만 따로 잰 것(640×480 한 장면을 200 번):

| | 전 | 후 |
|---|---|---|
| 컬러 + 깊이 압축 ms/장 | 3.35 | 2.87 |
| 그 가운데 LZ4(컬러) | 1.6 | 1.6 |
| 장면당 새로 잡는 작업 버퍼 | 3 개(2.7 MB) | 0 (스레드마다 하나를 다시 씀) |
| 컬러를 훑는 횟수 | 채널마다 한 번씩 3 번 | 1 번 |

- 바꾼 것: 차이 값을 채우는 작업 버퍼를 다시 쓰고, 컬러는 한 번 훑으며 세 채널을 채우고, 깊이는 미터 → mm 변환과 차이 계산을 한 번에 한다.
- 값은 같다: 압축한 바이트가 앞의 계산과 같은지 시험(`pack_matches_reference`, 크기 7 가지)으로 보고, 같은 스트림 300 장을 옛·새 memmap 에 넣어 나온 파일 311 개가 모두 같다.
- 남은 시간의 절반 넘게가 LZ4 자체다. 실시간 재생에서 압축 한 번의 시간은 실행마다 1.9 ~ 2.2 ms 로 흔들려 0.5 ms 차이는 그 안에 든다.

## 물체 사진 벡터·글 검색·사진 벡터 병합 (데스크톱 WSL, TUM fr1_room, 2026-11-12)

## SigLIP2 를 NPU 용(.dxnn)으로 바꿔 보기 (데스크톱 WSL, DX-COM 2.5.0, 2026-11-12)

보정 자료: fr1_room 물체 사진 46 장(영상 인코더), 물체 이름·질의 문장 314 개(글 인코더).

| 대상 | 방법 | 결과 |
|---|---|---|
| 영상 인코더 | 8 비트 기본(EMA 보정) | 변환됨. 원본과의 코사인 0.27(QSNR −1.8 dB), 가중치만 8 비트일 때는 0.996 |
| 영상 인코더 | 보정 방법만 바꿈(IQR, MinMax) | 코사인 0.28(QSNR −1.9 dB) |
| 영상 인코더 | 정확도 보강 자동(Q-PRO, P0 → P1 → P3/P4) | P3/P4 단계에서 컴파일러 오류로 끝남 |
| 영상 인코더 | 정확도 보강을 하나씩(IQR 재보정, P0, P1, P2) | 넷 다 변환됨(각 110 MB). 컴파일러가 이 경로에서는 정확도를 내주지 않아 코사인은 재지 못했다 |
| 영상 인코더 | 정확도 보강 자동(Q-PRO) 다시, 보정 사진 788 장 | 끝까지 돌아 변환됨(46 분, 110 MB). 코사인 0.20(QSNR −2.2 dB), 가중치만 8 비트일 때는 0.9999 |
| 글 인코더 | 8 비트 기본(EMA 보정) | 변환됨(88 MB). 코사인 0.64(QSNR 2.3 dB), 가중치만 8 비트일 때는 0.9999 |

- 두 인코더 모두 오차는 층 사이를 오가는 값(활성값)을 8 비트로 줄이는 데서 난다. 코사인 0.27 · 0.64 는 검색·병합에 쓸 수 없는 값이라 사진 벡터와 글 벡터는 CPU(ONNX)로 계산한다.
- 하나씩 보강한 파일 넷의 정확도는 보드의 NPU 에서 돌려 ONNX 벡터와 견주어야 알 수 있다.
- 글 인코더는 토큰 번호(정수) 입력을 NPU 가 받지 않아 둘로 나눴다: 토큰 표 찾기 + 위치 더하기는 CPU, 그 뒤 층은 NPU 모델(입력 `[1, 64, 768]`).
- 원본 ONNX 는 묶음 연산(`Attention`)과 16 비트 가중치라 컴파일러가 받지 않는다. `model.safetensors` 에서 32 비트·기본 연산으로 다시 내보낸 것을 넣었다.
- 보드에서의 NPU 실행 시간은 재지 않았다.

### 왜 깨지는가: 층 사이 값의 범위 (영상 인코더, 보정 사진 8 장으로 층마다 잼)

| 자리 | 가장 큰 값 | 보통 크기(RMS) |
|---|---|---|
| 블록 1 ~ 5 를 지난 값 | 5 ~ 22 | 0.5 |
| 블록 6 ~ 9 를 지난 값 | 220 ~ 230 | 1.5 |
| 블록 10 ~ 12 를 지난 값 | 420 ~ 630 | 3 ~ 4.5 |
| 블록 10 의 MLP 가운데 값 | 약 1,200 | 0.2 |

- 큰 값은 블록 6 의 MLP 에서 처음 생기고, 토큰 64 개 가운데 1 개, 채널 768 개 가운데 4 개(67 · 145 · 301 · 483)에만 실린다. 사진이 바뀌어도 크기가 거의 같다.
- NPU 는 한 층의 값 전체를 256 단계 하나로 나눈다. 범위가 600 이면 한 칸이 약 4 라서 크기 1 ~ 2 인 나머지 값이 모두 0 이 된다. 보정 사진 수와 정확도 보강이 코사인을 올리지 못한 까닭이다.
- 정규화(LayerNorm)와 활성 함수(GELU)는 컴파일러가 스스로 한 연산으로 묶는다. 묶인 연산으로 직접 내보내면(opset 20) 인코더 전체가 CPU 로 배정된다.

### 앞 5 블록만 NPU 로 (보정 사진 200 장, 8 비트 기본)

| 자른 자리(NPU 출력) | NPU 배정 | 원본과의 코사인 |
|---|---|---|
| 블록 6 의 첫 정규화 출력 | 앞 5 블록 전부(38 MB) | 0.964 (QSNR 11.5 dB), 가중치만 8 비트일 때 0.999 |

### 구조를 바꿔 8 비트로: 코사인 0.99 (영상 인코더, 보정 사진 200 장, 2026-11-13)

가중치를 다시 배우지 않고, 출력이 같은 모양으로 모델을 바꿔 내보낸 뒤 8 비트 기본(EMA 보정)으로 컴파일했다. 코사인은 컴파일러 진단이 낸 끝 벡터 기준 값이다.

| 내보낸 모델 | 코사인 | 활성값만 8 비트 | 가중치만 8 비트 |
|---|---|---|---|
| ① 큰 값이 실리는 토큰 2 개를 상수로 고정 | 0.849 (QSNR 4.7 dB) | 0.852 | 0.9994 |
| ② ① + 잔차 채널을 무작위 회전으로 섞음 | 0.852 (4.7 dB) | 0.840 | 0.998 |
| ③ ② + GELU 출력을 둘로 나눔 | 0.987 (15.7 dB) | 0.987 | 0.998 |
| ④ ③ + 회전을 값 범위가 좁아지게 고름 | **0.9875** (16.0 dB) | 0.988 | 0.9993 |

- ① 토큰 고정: 큰 값은 토큰 15(블록 6 부터)와 토큰 7(블록 10 부터)에만 실리고 사진이 바뀌어도 거의 같다. 그 토큰의 갱신을 멈추고, 다른 토큰이 그 토큰을 볼 때 쓰는 값은 평균값에서 미리 계산한 상수로 넣는다.
- ② 회전: 잔차 흐름 768 채널에 직교 행렬을 곱하고, 정규화의 배율·편향은 이웃한 선형 층 가중치에 합친다. 채널 몇 개에 몰린 값이 전체로 퍼진다.
- ③ GELU 나누기: MLP 가운데 값 f 를 `a = GELU(min(f, 2))` 와 `b = ReLU(f − 2)` 로 나누고 `fc2(a) + W·b` 로 합친다(2 이상에서 GELU(x) ≈ x). GELU 출력은 보통 크기 0.2 ~ 0.9 에 최대 4 ~ 104 라서 한 텐서로 두면 256 단계가 큰 값 몇 개에 다 쓰인다. 나누면 a 는 −0.17 ~ 1.95 로 촘촘하고 b 는 대부분 0 이다. 블록마다 3072 → 768 행렬곱이 하나 는다.
- ④ 회전 고르기: 사진 197 장의 잔차 값에서 12 제곱 평균이 작아지는 쪽으로 직교 행렬을 경사 하강(1,500 번)했다. 입력 임베딩의 최대 절댓값 4.9 → 2.0, 마지막 블록 뒤 33.9 → 10.8.
- ①~④를 다 넣은 실수(32 비트) 모델과 원본의 코사인은 0.9999 다.
- 결과 파일 146 MB, 인코더 본체는 NPU 묶음 하나에 들어간다.

## 보드 위치 추적: 장면 읽기 스레드 (Pi 5, fr1 책상 1 배 재생 3 번씩, 2026-11-14)

장면 읽기(카메라 대기·깊이 정렬, 재생은 PNG 풀기 12 ms)를 따로 도는 스레드로 옮겨 위치 추적이 읽기를 기다리지 않게 했다. 위치 추적이 밀리면 아직 안 가져간 장면을 새 장면으로 바꾼다(카메라처럼). 위치 추적 설정(특징점 400)은 그대로다.

| | 처리한 장면(장/초) | memmap 이 받은 장면 | 위치 오차 |
|---|---|---|---|
| 읽기 스레드 없음 | 24.9 · 25.3 · 25.1 | 255 · 260 · 258 | 4.4 · 5.1 · 8.0 cm |
| 읽기 스레드 | 28.7 · 28.6 · 28.5 | 294 · 293 · 292 | 6.0 · 6.1 · 6.2 cm |

- 오차는 같은 범위이고 덜 흔들린다. 같은 시점 화면도 같다(모니터 윤곽은 읽기 스레드 쪽이 덜 겹침).
- 같은 날 특징점 300 을 함께 넣었을 때 점군이 번져 보여 둘 다 되돌렸다가, 읽기 스레드만 따로 재서 다시 넣었다. 특징점은 400 으로 둔다.
- memmap 은 이 재생에서 코어 하나쯤(CPU 21 초 / 20 초)을 쓰고, 분할 · 사진 벡터를 따라온다. 처리량의 한계는 위치 추적이다.

## 뷰어 벽 계산 C++ → Rust (데스크톱 WSL, 2026-11-14)

`viewer/sgview` 의 벽 선분·상태 벡터 계산(walls.cpp 529 줄)을 `src/walls.rs` 로 옮기고 C++ 빌드를 없앴다. 원본 C++ 를 같은 `-O3` 로 빌드해 나란히 돌려 비교했다.

- 입력: 실제 지도 20 개(가구 영역 3 가지 × 무작위로 돌린 사본 4 개), 기울어진 벽 합성 방 1,500 개, 잡음·경계 격자 3,000 개(0×0, 1×N, 전부 점유·미지 포함).
- 결과: 선분 + 벽 방향 4,680 건, 상태 벡터 74,860 건 모두 비트 동일(선분 213,889 개). 같은 거리의 선분 순서까지 같게 libstdc++ 의 partial_sort 힙 순서를 그대로 옮겼다.
- 속도(지도 20 개 합계): 선분 C++ 26.0 – 27.5 ms, Rust 27.0 – 27.8 ms. 상태 벡터 13 – 14 µs, 13 µs. 축 정렬 지도 하나는 Rust 가 0.1 ms 느리고(0.15 → 0.25 ms) 기울어진 지도는 같거나 Rust 가 빠르다.

## SLAM Rust 이식: 단어 사전(FLANN) · 입출력 (데스크톱 WSL, 2026-11-14)

RTAB-Map 이 쓰는 경로를 `slam/` 크레이트로 옮기며 조각마다 원본(WSL `~/opt/rtabmap_bg`, `opencv_bg`)과 같은 입력으로 비트 비교한다.

- **단어 사전(rtflann KD-트리 4 개, checks 32, L1 거리)**: fr1_desk 613 장면 전체에서 찾기 159,029 번 · 넣기 55,243 번 · 지우기 25,752 개 + 다시 만들기 1 번이 원본과 불일치 0. 찾기 2,460 → 약 860 ms, 만들기·넣기 150 → 123 ms. BRIEF 의 0/1 실수 256 개 L1 거리를 묶은 비트의 popcount 로 구해 값이 같고 메모리는 32 배 작다. 원본은 나무마다 `std::random_device` 씨앗을 받아 실행마다 결과가 달라서, 비교 때는 원본 씨앗을 고정하고 Rust 가 같은 난수 순서를 따른다.
- **입출력**: 회색조(OpenCV 4.10 계수 3735/19235/9798 ≫ 15)와 깊이 mm 가 fr1_desk 613 장 · 복도 1,658 장 모두 같고, memmap 으로 가는 스트림이 942 MB · 2.55 GB 전체 바이트까지 같다. 장면 읽기 49 – 53 ms/장(원본, RTAB-Map 과 함께) → 7.7 – 8.0 ms/장(단독) · 12.9 ms(함께), 스트림 쓰기 1.03 → 0.30 ms/장.
- **특징점(GFTT + BRIEF + 3D 점, `slam/src/features.rs`)**: fr1_desk 613 장 · 복도 1,658 장 전체(특징점 233,266 · 606,482 개, 1 · 4 스레드 모두)와 앞서 잰 각 200 장 전부 원본(RTAB-Map `generateKeypoints` → `generateDescriptors` → `generateKeypoints3D`)과 특징점 순서·x·y·response·size·angle·octave, 3D 점 f32, 설명자 32 바이트까지 비트 동일(특징점 75,489 · 70,810 개). 4.40 – 4.68 → 1.40 – 1.48 ms/장(약 3 배, 1 스레드). 빨라진 곳: 최댓값 거르기(dilate)를 문턱·가로·세로 최댓값으로 나눠 한 번에, 가리개 안 최댓값을 고유값 계산 중에 함께, 위쪽만 먼저 정렬, BRIEF 의 9×9 합 그림을 한 번 만들어 적분 그림 네 번 읽기를 한 번으로, 큰 버퍼 재사용. 비교는 x86 PC 원본과 했고, 보드(aarch64, 원본 OpenCV 가 NEON 곱셈-덧셈 합침을 씀)는 보드에서 같은 비교로 확인한다.
