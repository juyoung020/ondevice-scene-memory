# 일반 카메라로 포즈와 3D 지도 얻기

USB RGB 카메라에는 깊이도 IMU 도 없다. 그래서 두 가지를 영상만으로 풀어야 한다.

- **포즈**: 카메라가 지금 어디서 어느 쪽을 보는지 (6자유도)
- **깊이**: 화면의 각 점이 얼마나 먼지 → 3D 점

단안 카메라만의 고유 문제:

| 문제 | 왜 생기나 |
|---|---|
| 크기 모호성 | 작은 방을 가까이서 본 것과 큰 방을 멀리서 본 것이 똑같이 찍힘 → 미터 단위가 안 나옴 |
| 크기 떠밀림 | 오래 움직이면 그 비율이 조금씩 변함 |
| 초기화 | 제자리 회전만 하면 깊이 단서가 없어 시작을 못 함 |
| 흐림·무늬 없는 벽 | 특징점이 안 잡혀 추적이 끊김 |

## 포즈 후보

| # | 방법 | 크기(m) | 손떨림·흰 벽 | 보드에서 | NPU 쓰임 |
|---|---|---|---|---|---|
| 1 | **고전 단안 SLAM** (ORB-SLAM3 단안, stella_vslam) | 없음 → 깊이 모델이나 마커로 맞춰야 함 | 약함 | CPU 로 가능 | 없음 |
| 2 | **가짜 RGB-D**: NPU 깊이 모델 출력을 깊이 카메라처럼 RGB-D SLAM 에 넣음 (ORB-SLAM3 RGB-D 모드) | 깊이 모델이 줌 | 초기화 즉시, 제자리 회전 OK | 깊이 모델이 추적 속도만큼 빨라야 함 | 깊이 |
| 3 | **학습 특징점 + 고전 최적화**: 특징점 추출(XFeat / SuperPoint)을 NPU 에서, 매칭·BA 는 CPU | 2 와 같이 깊이로 | ORB 보다 강함 | 가능성 높음 | 특징점 + 깊이 |
| 4 | **학습형 SLAM 통째로** (DROID-SLAM, DPVO, MASt3R-SLAM, VGGT 류) | 일부 줌 | 가장 강함 | 큰 GPU 전제, DX-M1 엔 무거움 | — (PC 기준선으로만) |
| 5 | **IMU 하나 추가** (값싼 6축 센서) → VIO (VINS-Mono, OpenVINS) | IMU 가 줌 | 강함 | CPU 로 가능 | 없음 |

추천 출발점: **2번**(NPU 깊이 → RGB-D SLAM). 크기·초기화 문제가 한 번에 풀리고 NPU 를 핵심에 쓴다.
더 갈 곳: **3번**(SLAM 앞단을 NPU 로 포팅 — 온디바이스 과목에 가장 잘 맞는 기여). 4번은 PC 에서 정답에 가까운 기준선으로 비교용.
5번은 하드웨어가 하나 늘지만 가장 확실하다 — 2·3 이 손떨림에 무너지면 꺼낸다.

## 크기(m) 를 YOLO 로 잡기 — 물체 크기 앵커

YOLO-seg 를 **우리가 고른 물체로 직접 학습**하므로, 각 물체의 실제 크기를 줄자로 재 두면 정확한 크기 사전값이 생긴다.
그 물체가 보일 때마다 크기 기준이 하나 생기는 셈이다.

| 쓰는 법 | 식 | 비고 |
|---|---|---|
| 거리 바로 구하기 | 거리 Z = 초점거리 f × 실제 높이 H / 화면 높이 h(px) | 깊이 모델 없이 물체 3D 위치가 나옴. 한 장으로 됨 |
| SLAM 크기 맞추기 | 크기 비율 = 실제 크기 / SLAM 좌표로 복원한 그 물체 점구름 크기 | 여러 물체·여러 프레임 중앙값 → 1번 단안 SLAM 의 크기 모호성·떠밀림을 계속 보정 |
| 깊이 모델 크기 맞추기 | 마스크 안 깊이 중앙값 ↔ 위 거리 Z | 2번의 프레임별 크기 맞춤 기준으로 SLAM 점 대신·같이 사용 |

조심할 것:
- 화면 가장자리에 **잘린 물체**, **가려진 물체**는 크기를 틀리게 준다 → 마스크가 화면 끝에 닿거나 깊이상 가려지면 앵커에서 뺀다.
- 박스 높이는 **보는 각도**에 따라 변한다 (눕힌 컵) → 높이·너비 중 방향에 덜 민감한 값(세워 두는 물체의 높이), 또는 3D 점구름 크기 비교를 우선.
- 같은 클래스라도 크기가 다른 물체가 여럿이면 → 우리 데이터에선 물체 하나 = 클래스 하나로 두거나, 크기 편차가 작은 것(A4 종이, 모니터, 문 등)만 앵커로.
- 앵커 한 번은 잡음이 크다 → 시간에 따라 이상치 빼고 중앙값.

효과: **1번(단안 SLAM) + 물체 크기 앵커**만으로도 미터 단위 지도와 물체 위치가 나온다 → 깊이 모델 없이도 끝까지 가는 가장 가벼운 길. 깊이 모델은 물체의 모양(점구름)과 빈 공간 지도를 더 촘촘히 하는 데 쓴다.
초기화(제자리 회전)·흰 벽 끊김은 크기 앵커로 안 풀린다 — 그건 여전히 2·3·5번 몫.

## IMU 를 붙이면 (5번 자세히)

| 문제 | IMU 로 | 이유 |
|---|---|---|
| 크기(m) | 풀림 | 가속도계가 실제 m/s² 를 잼. 단 카메라를 흔들어 가속이 있어야 보임(시작할 때 몇 초 이리저리) |
| 중력 방향(바닥이 어디) | 풀림 | 지도가 항상 똑바로 섬 → "위에" 관계 판단이 쉬워짐 |
| 제자리 회전 | 풀림 | 자이로가 회전을 직접 잼 |
| 빠른 움직임·흐림 | 짧게는 풀림 | 영상이 1초 이내 끊겨도 IMU 로 이어 감 |
| 흰 벽을 오래 봄 | 안 풀림 | 값싼 IMU 만으로는 몇 초 만에 위치가 m 단위로 틀어짐 |
| 오래 돌면 쌓이는 오차 | 안 풀림 | 같은 곳을 다시 볼 때 영상으로 고치는 루프 클로징 몫 |
| 물체 3D 점·빈 공간 지도 | 안 풀림 | 깊이는 여전히 깊이 모델·YOLO 크기 몫 |

진짜 비용은 센서값이 아니라 **맞추기**다.
- **시각 맞추기**: USB 카메라는 찍은 시각이 수십 ms 흔들린다. VIO 는 이 어긋남에 민감 → 시각 차이를 함께 추정하는 방식(OpenVINS 온라인 보정, Kalibr 로 처음 값) 필요.
- **장착 위치 보정**: 카메라와 IMU 를 단단히 한 몸으로 고정하고, 둘 사이 위치·방향을 Kalibr 로 한 번 잼 (AprilGrid 판 앞에서 흔들며 촬영).
- **롤링 셔터**: 일반 웹캠은 줄마다 찍는 시각이 달라 빨리 돌리면 휘어 보임 → 천천히 촬영하거나 글로벌 셔터 카메라.

고른 것: ICM-42688-P (아래 하드웨어 결정). 소프트웨어는 롤링셔터 모델이 있는 VINS-Mono/VINS-Fusion 1순위, ORB-SLAM3 단안-관성·OpenVINS 비교.

## IMU ↔ Pi5 연결 (납땜 없음)

IMU: **SparkFun 9DoF IMU Breakout — ISM330DHCX + MMC5983MA (Qwiic, SEN-19895)**. 산업용 6축(자이로 약 5 mdps/√Hz, 가속도 약 60 µg/√Hz, FIFO 에 칩 시각 기록) + 지자기(안 씀). Qwiic 커넥터라 케이블만 꽂는다.
케이블: Qwiic(JST-SH 1.0 4핀) → 듀폰 **암** 4가닥, Pi 40핀 헤더에 바로 꽂음.

| Qwiic 선 (표준 색) | Pi5 핀 번호 | Pi5 신호 |
|---|---|---|
| 검정 GND | 6 | GND |
| 빨강 3.3V | 1 | 3V3 |
| 파랑 SDA | 3 | GPIO2 (I2C1 SDA) |
| 노랑 SCL | 5 | GPIO3 (I2C1 SCL) |

색이 표준과 다를 수 있으니 Qwiic 커넥터 쪽 핀 순서(GND·3V3·SDA·SCL)로 확인.

- 켜기: `/boot/firmware/config.txt` 에 `dtparam=i2c_arm=on`, `dtparam=i2c_arm_baudrate=400000` → `/dev/i2c-1`. 주소 ISM330DHCX 0x6B, MMC5983MA 0x30 (`i2cdetect -y 1` 로 확인).
- 읽기: **우리 프로그램이 /dev/i2c-1 로 직접** FIFO 를 묶음으로 읽는다. 시각은 FIFO 안 칩 시각(타임스탬프 배칭)을 Pi monotonic 시계에 맞춰 붙인다 — 인터럽트 선이 없어도 됨.
  - 라즈베리파이 커널에는 이 칩 드라이버(`st_lsm6dsx`)가 켜져 있지 않다(bcm2712_defconfig, 2026-10-28 확인) → 커널에 기대지 않는다.
- 400 kHz I2C 로 6축 1 kHz(초당 약 14 KB)까지 여유.
- 받으면 먼저: WHO_AM_I(0x0F) = 0x6B 확인, 가만히 둔 채 몇 분 기록해 잡음 재기.
- 실물 확인: DX-M1 HAT 가 40핀 헤더를 덮으면 핀 연장 헤더 필요.
- 처음 고른 ICM-42688-P(알리 범용 기판)는 핀헤더 납땜이 필요할 수 있어 뺐다.

## 일반 카메라 + IMU 로 포즈를 확실하게

| # | 할 것 | 왜 |
|---|---|---|
| 1 | **롤링셔터를 모델로 보정** — VINS-Mono/VINS-Fusion 의 롤링셔터 설정(`rolling_shutter: 1`, 줄 읽는 시간 `rolling_shutter_tr`)을 켜고, 읽는 시간은 Kalibr 로 잼 | 화면 휨을 "버티기"가 아니라 계산에 넣음. 1순위 VIO 를 VINS 계열로 두는 이유 |
| 2 | **노출 고정·짧게** (자동 노출·자동 화이트밸런스 끔, 노출 수 ms) | 흐림 감소 + 프레임마다 노출이 바뀌어 시각이 흔들리는 것 방지 |
| 3 | **낮은 해상도·높은 fps** (카메라가 주는 가장 높은 fps, 예: 640×480) | 한 화면 읽는 시간이 짧아져 휨이 줄고, 추적이 촘촘해짐. 고해상도는 YOLO 용 키프레임에서만 |
| 4 | **같은 시계**: 카메라 프레임(V4L2 버퍼 시각)과 IMU(FIFO 칩 시각을 Pi 시계에 맞춤) 둘 다 Pi 의 monotonic 시계 | 남는 고정 지연은 VIO 가 온라인 추정(VINS `estimate_td: 1`) |
| 5 | **단단한 한 몸 거치** + Kalibr 보정 (카메라 내부값, 카메라-IMU 위치·방향, 시각 차이, 롤링셔터 읽는 시간) | 보정이 틀리면 나머지가 다 무너짐 |
| 6 | **시작 동작 정하기** — 켜고 2~3초 이리저리 흔들어 IMU 초기화 | 단안 VIO 는 가속이 있어야 크기(m)가 잡힘 |
| 7 | **루프 클로징 켜기** + 한 바퀴 돌아 시작점 다시 보기 | 오래 돌며 쌓인 오차를 영상으로 되돌림 |
| 8 | **크기 검증**: YOLO 물체 크기 앵커로 m 단위가 맞는지 계속 확인, 크게 어긋나면 경고 | VIO 크기가 틀어지는 걸 바로 알아챔 |

확실한지 재는 법:
- 닫힌 경로 걷기 → 시작점으로 돌아왔을 때 어긋난 거리 / 걸은 거리 (%)
- 바닥·책상에 ArUco 마커 몇 장 → 마커로 구한 포즈와 VIO 포즈 비교 (cm, °)
- 줄자로 잰 두 물체 사이 거리 vs 지도 위 거리
- 같은 경로를 롤링셔터 보정 끔/켬, 노출 자동/고정으로 비교 → 무엇이 효과 있었는지 숫자로

이렇게 해도 손떨림·빠른 회전에서 무너지면 그때 글로벌셔터 카메라(ELP AR0234 컬러, 약 11만 원)를 다시 검토한다.

## 3D 지도 갱신

### 1. 지도를 키프레임에 묶어 둔다

물체 점·깊이 점을 **전역 좌표로 바로 굳히지 않고**, 그걸 본 키프레임 기준 좌표로 저장한다.
전역 위치 = 키프레임 포즈 × 키프레임 안 좌표.
루프 클로징·BA 로 포즈가 고쳐지면 지도도 다시 계산할 필요 없이 따라 고쳐진다.

### 2. 깊이 크기를 프레임마다 맞춘다

깊이 모델은 프레임마다 크기가 조금씩 흔들린다. 매 키프레임 SLAM 이 가진 희소 3D 점과 깊이 모델 값을 비교해 `크기·오프셋`을 최소제곱(이상치 제거)으로 맞춘 뒤 쓴다. 이렇게 하면 같은 물체가 프레임마다 번지지 않는다.

### 3. 지도 표현

| 층 | 무엇 | 왜 |
|---|---|---|
| 희소 점 | SLAM 이 쓰는 특징점 | 포즈 추적용 |
| 거친 점유 격자 (복셀) | 공간 모양 | 뷰어 배경, "이 근처가 비었나" |
| 물체 점구름 | 물체마다 마스크에서 뽑은 3D 점 | 위치·크기·관계 계산 |

### 4. 물체 바뀜 처리

| 상황 | 판단 |
|---|---|
| 기억 속 물체 자리가 지금 화면에 보이는데(깊이로 가려짐 아님 확인) 검출이 안 됨 | 있을 확률 ↓ → 일정 이하면 "사라짐" |
| 다른 곳에서 벡터가 아주 비슷한 같은 클래스가 보임 | "옮겨짐" → 위치 갱신 |
| 처음 보는 것 | 새 노드 |

## 비교 방법 (보드 전에 PC 에서)

1. **정답 포즈 있는 공개 데이터**: TUM RGB-D (깊이는 버리고 RGB 만 사용, 정답 깊이는 깊이 모델 평가에 사용), ScanNet 일부. 후보마다 ATE(cm)·크기 오차·끊긴 횟수.
2. **우리 카메라로 찍은 손 영상**: 실제 USB 카메라·손떨림·흐림 조건. 책상에 ArUco 마커 몇 장 → 마커로 정답 포즈 근사.
3. 이긴 방법을 보드로 옮겨 같은 영상으로 다시 재기 (PC vs 보드 차이 = 양자화·속도 영향).

## 먼저 확인할 것

- 깊이 모델 후보들이 DX 컴파일러에서 `.dxnn` 이 되는지, 되면 NPU 에서 몇 ms 인지 (2번 성립 조건)
- XFeat / SuperPoint 가 `.dxnn` 이 되는지 (3번 성립 조건)
- ORB-SLAM3 가 Pi5 에서 빌드·실시간 되는지
